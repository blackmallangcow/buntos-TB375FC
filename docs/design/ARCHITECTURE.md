## 1. 배경과 문제 정의

안드로이드 태블릿은 하드웨어 성능에 비해 활용성이 낮다.

| 제약 | 안드로이드에서의 원인 | buntOS에서의 해결 방향 |
|---|---|---|
| 셸/CMD 제어 불가 | 앱 샌드박스, root 미제공, SELinux 강제 정책 | 표준 Unix 셸과 사용자 소유 root(sudo)를 기본 제공 |
| 개발환경 구성 불가 | bionic libc, 패키지 매니저 부재, Termux는 앱 샌드박스 내부 | glibc 기반 범용 배포판 패키지 생태계 그대로 사용 |
| 테스트 호스팅 불가 | Doze/백그라운드 프로세스 강제 종료 | systemd 서비스 + 명시적 전원 정책(호스팅 모드) |
| 앱 간 제어 불가 | 앱 간 격리, 접근성 API 제한 | OS 레벨 Agent Control Plane이 권한 기반으로 앱 간 제어 제공 |

목표는 "태블릿 폼팩터의 개발용 Unix 워크스테이션"이다. 이를 위해 다음 두 가지는 타협하지 않는다.

1. **완전히 열린 스택** (D8, 정의는 2.1절): 위 제약은 모두 사용자가 통제할 수 없는 코드(벤더 프레임워크, 벤더 커널, 폐쇄 드라이버)에서 나온다. 사용자 공간만 바꾸고 그 아래를 벤더 코드로 남기면 같은 문제가 다른 층에서 다시 생긴다
2. **OS는 개발환경 구성을 막지 않는다** (D9): root, 패키지 설치, 컨테이너, 가상화, 커널 모듈 빌드, 커널 업그레이드를 OS 구성이 막아서는 안 된다

## 2. 핵심 설계 결정 (요약)

| # | 결정 | 이유 |
|---|---|---|
| D1 | 커널은 **Linux**를 사용하고 자체 커널을 작성하지 않는다 | 목표가 "Unix 생태계 흡수"다. 자체 커널은 바이너리/드라이버 호환성을 처음부터 잃는다. buntOS의 차별점은 커널이 아니라 사용자 공간(UI, AI 제어 계층, 통합 경험)이다 |
| D2 | 사용자 공간 베이스는 **Debian (glibc, systemd)**. 기준은 **forky(testing) 스냅샷 고정**이며 forky 정식 릴리스 시 stable로 전환한다(ADR-004) | arm64 / amd64 모두 1급(official) 아키텍처로 패키지 동등성이 가장 높다. musl 기반(Alpine)은 Node/Python 휠 등 사전 빌드 바이너리 호환성 문제가 있어 개발 머신용으로 부적합. forky는 실기기 GPU에 필요한 커널 6.18 이상과 Mesa 25.1 이상을 기본 저장소에 갖고 있고, 실측을 출시할 플랫폼에서 한 번만 하면 된다 |
| D3 | 두 아키텍처는 **동일한 소스, 동일한 패키지 목록, 동일한 이미지 레시피**에서 빌드하고, 차이는 BSP(Board Support Package) 계층에만 허용한다 | 제1 목표(지원 동등성)를 구조적으로 강제 |
| D4 | 디스플레이 서버는 **Wayland**, 컴포지터는 **Rust + Smithay** 기반 자체 구현 (`bunt-comp`) | macOS 수준 UI와 AI 제어 계층(가상 seat, 오프스크린 출력)을 컴포지터 내부에 넣어야 하므로 기존 DE 테마 수정으로는 불가. Rust는 GC 없이 메모리 안전성 확보. Smithay는 GLES/pixman(소프트웨어) 렌더러를 모두 제공하여 GPU 드라이버 불확실성에 대응 가능 |
| D5 | AI 제어는 **비전(스크린샷) 우선이 아니라 의미 구조(semantic) 우선**: CLI/D-Bus 액션 > 접근성 트리 > 스크린샷 순 | Aside의 설계 원칙 채택 (6장) |
| D6 | 파일시스템은 **btrfs + 트랜잭션 단위 스냅샷**, 부트 파티션은 A/B | 개발 머신은 패키지를 자유롭게 설치해야 하므로 불변(immutable) 루트는 장벽이 된다. 대신 롤백을 보장 |
| D7 | 설정값은 코드가 아닌 **선언형 설정(TOML)** 으로 분리 (보드 정의, 해상도/배율, 전원 정책, 권한 정책, 문자열) | 규칙 1 (하드코딩 금지) |
| D8 | **개방성**: 애플리케이션 프로세서(AP, 메인 CPU)에서 실행되는 커널·드라이버·사용자 공간 코드는 전부 오픈소스이며 업스트림을 목표로 한다. 벤더 커널, 폐쇄 커널 모듈, 폐쇄 사용자 공간 드라이버, bionic 호환 계층(libhybris)은 쓰지 않는다. 펌웨어만 예외다(2.1절) | 1장의 원인(bionic, 벤더 통제)을 구조적으로 제거한다. 커널을 업스트림과 함께 올릴 수 있어야 개발환경이 시간이 지나도 막히지 않는다(D9) |
| D9 | **개발환경 비차단**: root, 패키지 설치, 컨테이너(rootful/rootless), 가상화(KVM), 커널 모듈 빌드, 커널 업그레이드를 OS 구성이 막지 않는다. 하드웨어나 펌웨어가 막는 경우는 실측으로 확인해 원인과 함께 기록한다 | 1장의 목표 그 자체. 검증은 동등성 기능 매트릭스(4.4)와 실측(12장)으로 한다 |
| D10 | **라이선스**: 컴포지터(bunt-comp), 셸(bunt-shell), 에이전트(buntd-agent, bunt CLI, MCP 어댑터 서버)는 GPL-3.0-or-later. 외부 앱이 링크하는 SDK·프로토콜 크레이트는 MIT OR Apache-2.0. 문서는 CC BY-SA 4.0. 기여는 DCO, 표기는 파일 단위 SPDX 헤더(REUSE 규격)로 한다(ADR-006) | buntOS는 오픈소스로 공개한다. GPLv3는 소비자 기기에 실어 배포하는 쪽에 수정 버전 설치 정보(Installation Information)를 요구하므로, 파생 기기가 다시 잠기는 것을 막아 D8·D9를 파생물까지 잇는다. SDK는 permissive로 두어 앱 생태계를 막지 않는다(D9) |

### 2.1 개방성 정의 (D8 상세)

적용 범위는 **OS가 기본 제공하거나 OS 동작이 의존하는 코드**다. 사용자가 직접 설치하는 소프트웨어는 폐쇄 앱이라도 사용자의 선택이며, D9에 따라 막지 않는다.

| 계층 | 예 | 요구 |
|---|---|---|
| AP 사용자 공간 | 셸, 시스템 앱, Mesa, PipeWire, 네트워크 서비스 | 오픈소스 필수. 폐쇄 바이너리와 bionic 호환 계층 금지 |
| AP 커널 | 커널, 드라이버, DTS | 오픈소스 필수. BSP 패치는 업스트림 제출이 기본이고, 다운스트림 패치는 제출 대기열로만 유지한다. 벤더 커널과 폐쇄 모듈 금지 |
| 펌웨어 | GPU, Wi-Fi/BT, 전원 관리 MCU 등 AP가 아닌 프로세서에서 실행되는 코드 | 예외로 허용. 선호 순서: 오픈소스 > 재배포 가능한 바이너리(linux-firmware 등) > 기기에서 추출하는 재배포 불가 바이너리(아래 규칙 조건으로 허용, ADR-012) |
| 부트 체인과 런타임 펌웨어 | preloader, LK, TF-A, TEE | 지금은 교체할 수 없으므로 범위 밖으로 두고 요구 사항으로 관리한다: (1) 사용자가 자기 커널을 부팅할 수 있어야 한다(언락), (2) EL2를 OS에 넘기는지 실측한다(12.1절), (3) 오픈 부트 체인으로의 교체는 장기 과제 |

이 선은 Debian의 non-free-firmware 구분과 같다. 펌웨어 목록은 BSP의 `board.toml`에 선언하고, 이미지에 포함하는 것(재배포 가능)과 설치 시 기기에서 추출하는 것을 구분한다.

재배포 불가 펌웨어 규칙 (ADR-012)

- 공개 이미지와 저장소에 절대 포함하지 않는다. 공개 이미지에 넣는 것 자체가 재배포다
- 설치 시 사용자 자신의 기기에서만 추출한다. 제3자 미러에서 받지 않는다
- 대상 파일과 해시는 `board.toml`에 선언하고, 추출 스크립트는 오픈소스로 둔다
- 추출에 실패하면 해당 기능만 비활성화되고 OS는 정상 부팅해야 한다
- 재배포 가능한 판이 나오면 그쪽으로 교체한다

#### 4.2.1 핵심 리스크 (v0.2 갱신)

1. **부트로더 언락이 비공식**: 레노버 공식 언락 채널이 TB375FC를 지원하지 않는다. XDA의 비공식 방법(LK 파티션 교체)이 존재하며 CN ROM ZUI 16 조건이 붙는다. 벽돌(brick) 위험 존재. CN 펌웨어 ZUI 16.0.20.091에서 언락과 AVB 해제 후 GSI 부팅에 성공한 보고가 있다(TrebleDroid 위키, 2025-08)
2. **MT6897 mainline 지원이 없다**: postmarketOS / mainline 커뮤니티에서 해당 SoC 포팅 사례를 찾지 못했다. 인접 SoC인 MT6878은 postmarketOS에 mainline 기반 커뮤니티 커널이 있다. 클럭, 전원 도메인, pinctrl, UFS, USB, PMIC, 디스플레이 파이프라인, 오디오를 직접 포팅해야 한다
3. **GPU는 업스트림이 지원한다**: Mesa Panfrost가 Mali-G615를 Valhall v11로 지원하고(GLES 3.1, Vulkan 1.4, OpenCL 3.0), 커널 Panthor는 Linux 6.18부터 Gx15 계열을 지원한다. 남은 일은 MT6897 쪽 GPU 전원·클럭 통합이다(추정)
4. **Wi-Fi/BT**: SoC 통합형인지, mainline 드라이버가 있는지 확인하지 못했다. 가장 큰 리스크 후보다
5. **디버그 채널**: UART가 노출되어 있지 않고, bring-up 초기에는 USB 드라이버도 없다(4.2.3)
6. **EL2 점유 가능성**: MediaTek에는 EL2에서 동작하는 자체 하이퍼바이저 GenieZone이 있다. 이 기기에서 GenieZone이 EL2를 차지하면 리눅스는 KVM을 쓸 수 없고, 이는 OS로 해결할 수 없다(D9). 12.1절에서 판정한다
7. **벤더 커널 소스 공개 미확인**: 공개되지 않으면 기기에서 추출한 벤더 DTB와 안드로이드에서의 동작 관찰이 주된 정보원이 된다. GPL 소스 공개 요청은 병행한다

#### 4.2.2 포팅 전략: mainline 단일 (v0.2 결정)

v0.1의 이중 트랙 중 **벤더 커널 하이브리드(구 Track A)는 폐기**하고 mainline(구 Track B) 하나로 간다. 구 Track A는 1장의 원인과 핵심 결정을 다음과 같이 충족하지 못한다.

| 기준 | 구 Track A의 결과 |
|---|---|
| 1장 원인 "bionic libc" | GPU 경로(libhybris + 벤더 블롭)로 bionic이 다시 들어온다. 블롭이 요구하는 안드로이드 HAL 서비스도 함께 구동해야 한다 |
| D8 개방성 | 디스플레이·터치·Wi-Fi·전원 드라이버(벤더 모듈)와 GPU 드라이버가 폐쇄 바이너리다 |
| D9 개발환경 비차단 | 커널이 벤더 모듈의 KMI(android14-6.1)에 묶여 버전 업그레이드와 구조체를 바꾸는 설정 변경이 막힌다. 출하 GKI에는 systemd 필수 옵션(`CONFIG_FHANDLE`), 컨테이너용 네임스페이스, btrfs가 빠져 있다. 브랜치 EOL은 2029-07-01 |
| D3 동등성 | BSP 경계 규칙을 완화해야만 성립하고, 커널 버전이 x86-64와 갈라진다 |
| 작업 재사용성 | 커널 재빌드와 KMI 검증, libhybris 백엔드, HAL 컨테이너는 mainline으로 이어지지 않는다 |

전략

- **업스트림 우선**: DTS와 드라이버는 업스트림(linux-mediatek 등) 제출을 기본으로 한다. `kernel/`의 다운스트림 패치는 제출 대기열로만 둔다
- **커널 계열 일치**: 실기기 커널은 x86-64와 같은 Debian 커널 계열에 BSP 설정 조각과 제출 대기 패치를 더해 빌드한다. 실기기 GPU에 필요한 커널 6.18 이상과 Mesa 25.1 이상은 forky 기본 저장소로 충족한다(ADR-004)
- **안드로이드의 역할**: OS 경로가 아니라 포팅 정보원이다. 벤더 DTB와 펌웨어 추출, 하드웨어 동작 관찰에 쓰며, 이를 위해 안드로이드 슬롯 하나를 보존한다(4.2.3)
- **렌더링**: GPU가 동작하기 전에는 pixman 소프트웨어 렌더러로 동작한다. 렌더러 추상화(D4)가 전환을 흡수한다
- **제품 개발과 병행**: 실기기 포팅은 Phase 3~5와 병행한다. 제품 기능의 종료 조건은 QEMU(양 아키텍처)에서 판정하므로 포팅 진척이 제품 개발을 막지 않는다

bring-up 단계 (각 단계는 측정 가능한 종료 조건을 가진다)

| 단계 | 내용 | 종료 조건 |
|---|---|---|
| 2a 최초 부팅 | 기기 부트로더(LK)에서 mainline 커널 + 최소 DTS(CPU, 메모리, 인터럽트, 타이머, 부트로더가 켜둔 화면의 simple-framebuffer. 가능 여부는 실측) | initramfs 셸 도달을 화면 콘솔 또는 재부팅 후 pstore 로그로 확인. 12.1절 EL2 최종 판정 |

#### 4.2.3 실기기 안전 수칙

- 어떤 플래시 작업 전에도 **전체 파티션 백업** (특히 `nvram`, `nvdata`, `nvcfg`, `protect1/2`, `persist` 계열: Wi-Fi MAC/캘리브레이션 데이터. 소실 시 복구 불가)
- 안드로이드 `recovery` 와 한쪽 슬롯은 보존하여 언제든 ZUI로 복귀 가능하게 유지 (포팅 정보원으로도 쓴다)
- 언락 조건이 특정 ZUI 버전에 묶여 있으므로 펌웨어 자동 업데이트(OTA)를 끈다
- 언락 진행 조건(go/no-go, ADR-011): (1) 전체 파티션 백업을 다른 기기로 옮겨 해시로 무결성 확인, (2) 언락 절차를 서로 독립된 보고 2개 이상으로 교차 확인하고 펌웨어 버전 일치 확인, (3) BROM/preloader 모드 복구 경로(mtkclient 등)의 MT6897 지원 사전 확인, (4) OTA 차단. 하나라도 빠지면 언락하지 않는다
- 기기에는 UART가 노출되어 있지 않다. 디버그 채널은 bring-up 단계에 맞춰 확보한다: (1) 부트로더가 켜둔 화면을 simple-framebuffer 콘솔로 쓴다, (2) pstore/ramoops로 직전 부팅의 커널 로그를 확보한다, (3) USB 포팅(2b) 후에는 **USB 가젯(configfs: ACM 시리얼 + NCM 이더넷)** 을 initramfs 최초 단계에서 띄운다

### 4.3 arm64 CI 기준 타깃: QEMU `virt` (aarch64, UEFI)

- 실기기 없이 모든 커밋에서 arm64를 검증하기 위한 기준 플랫폼
- x86-64와 동일한 e2e 시나리오를 그대로 실행하여 **동등성을 기계적으로 검증**
- 실기기 회귀는 별도 on-device 스모크 테스트로 보완 (9장)

### 4.4 동등성(제1 목표) 보장 장치

1. **패키지 동등성 리포트**: 빌드마다 아키텍처별 설치 패키지 목록과 버전을 비교. arm64에만 누락된 패키지가 있으면 릴리스 차단
2. **동일 기능 매트릭스**: 셸, sudo, systemd 서비스, podman/docker 호환, 툴체인(gcc/clang/rustup/node/python/go/jdk), SSH 서버, 로컬 호스팅(포트 바인딩, 리버스 프록시)을 e2e로 양쪽에서 실행
3. **x86-64 전용 바이너리 대응** (arm64에서): binfmt_misc + qemu-user-static(컨테이너 멀티아키 이미지), 사용자 바이너리용 FEX-Emu 또는 box64 중 성능 실측 후 택1
4. **호스팅 모드**: 전원 연결 시 `systemd-inhibit` 기반 서스펜드 억제, 화면 꺼짐 상태에서도 네트워크 서비스 유지. 정책은 TOML로 설정
5. **가상화(KVM)**: OS 구성은 KVM을 막지 않는다(커널 설정에 KVM 포함, `/dev/kvm` 접근 정책 제공). 실기기에서 실제로 쓸 수 있는지는 펌웨어가 EL2를 OS에 넘기는지에 달려 있으므로 12.1절에서 판정하고, 불가하면 원인과 함께 동등성 예외로 기록한다

## 5. UI/UX (제2 목표)

### 5.1 원칙

- 기준: macOS의 공간 구조(상단 메뉴바, 하단 Dock, 미션 컨트롤, Spotlight형 런처, 제어 센터, 알림 센터)와 상호작용 품질(관성 스크롤, 제스처 연속성, 120Hz급 애니메이션)
- **아키텍처와 무관하게 동일한 UI**. 폼팩터 차이는 "입력 모드"로만 다룬다
  - 포인터 모드(마우스/트랙패드): 데스크탑과 동일
  - 터치 모드: 히트 영역 확대, 화면 키보드 자동 표시, 가장자리 스와이프 제스처
  - 모드 전환은 하드웨어 이벤트(키보드 연결/분리, 포인터 장치 유무)로 자동. UI 레이아웃 자체는 바뀌지 않음
- 배율(scale)은 보드 정의 TOML의 패널 물리 크기와 해상도로 계산하며 분수 배율(wp-fractional-scale-v1)을 지원
- 화면별 모양, 토큰, 컴포넌트 규칙은 [디자인 스펙](DESIGN-SPEC.md)에 둔다. 기준은 macOS 26/27과 Apple HIG다

### 5.3 키보드 단축키

- macOS 26의 단축키를 기본으로 한다. ⌘는 Super 키(Mac 키보드의 Command, PC 키보드의 Windows 키)다. 모든 단축키를 컴포지터가 한 표(`comp/src/shortcuts.rs`)로 정한다. 사용자가 시스템 설정의 키보드 단축키 시트에서 바꾼 값은 `~/.config/buntos/comp-state.toml`의 `[shortcuts]`에 기본값과 다른 것만 적는다.
- 리눅스 앱은 Ctrl로 단축키를 받으므로, 컴포지터가 ⌘ 단축키를 포커스를 가진 앱이 아는 키로 옮겨 보낸다(⌘C → Ctrl+C). 누르고 있는 수정 키 가운데 보낼 키에 없는 것(⌘)은 잠시 떼었다가 다시 누르고, 필요한 수정 키(Ctrl)는 잠시 누른다. 앱과 입력기(fcitx5)는 정말 그렇게 누른 것처럼 받는다. Ctrl 단축키는 그대로 두므로 리눅스 방식도 된다.
  - 터미널(앱 ID로 안다)에는 터미널의 단축키(⌘C → Ctrl+Shift+C 등)를 보낸다. 터미널은 Ctrl+글자를 제어 문자로 쓰기 때문이다.
  - 텍스트 편집 키(⌘←, ⌥⌫ 등)는 포커스를 가진 앱이 글 입력(text-input-v3)을 켰을 때만 옮긴다. 켜지 않았으면 앱이 그대로 받는다(⌥←는 뒤로).
  - 앱은 옮긴 키를 한 번 눌렀다 뗀 것으로 받으므로, 누르고 있는 동안의 되풀이는 컴포지터가 키 반복 설정대로 한다.
- 컴포지터가 직접 하는 단축키: 앱·윈도우 전환(⌘⇥, ⌘\`), 앱 종료(⌘Q: 앱의 창을 모두 닫는다), 최소화와 가리기(⌘M, ⌘H, ⌥⌘H), 전체 화면(⌃⌘F), 스크린샷(⇧⌘3·⇧⌘4, ⌃를 더하면 클립보드), 입력 소스 전환, 화면 잠금(⌃⌘Q), 묻지 않는 로그아웃(⌥⇧⌘Q). 모든 앱 보기(⌘스페이스), Dock 가리기(⌥⌘D), 스크린샷 도구 막대(⇧⌘5), 로그아웃 확인 창(⇧⌘Q), 응용 프로그램 강제 종료 창(⌥⌘⎋)은 신호(`ShortcutActivated`)로 셸에 넘긴다.
  - ⌘⇥(앱 전환)는 컴포지터가 키를 받고, 최근 차례의 앱(앱 ID)과 고른 앱을 셸에 알린다(`AppSwitcherChanged`). 셸이 화면 가운데에 앱 전환 창을 그린다. ⌘를 떼면 고른 앱의 가장 최근 창을 앞으로 가져온다(macOS처럼 누르는 동안에는 바꾸지 않는다).
    - 전환 창이 떠 있는 동안 ⌘와 함께 누른 Esc(그만두기), Q(고른 앱 끝내기), H(가리기), ←·→·\`(고르기)는 전환 창의 키다.
    - 포인터로 가리키거나 누른 앱은 셸이 알린다(`SelectSwitcherApp`).
    - ⌘\`(같은 앱의 다른 윈도우)는 전환 창 없이 바로 바꾼다.
  - 화면이 잠긴 동안에는 입력 소스 전환, 가상 터미널 전환, 세션 끝내기(Ctrl+Alt+Backspace)만 듣는다(5.4절).
  - 최소화하거나 가린 창은 공간에서 내려 두고, 창 목록 프로토콜에 최소화로 알린다. 그 창을 활성화하면(Dock, 모든 앱, ⌘⇥, 에이전트) 제자리에 돌아온다.
    - 창의 최소화 단추(xdg_toplevel.set_minimized)도 받는다. 창 관리 기능(wm_capabilities)에 최소화를 알리므로 GTK 앱이 단추를 보인다.
    - 최소화한 창은 내리기 전에 그 창만 따로 그려(긴 변 256px) 셸에 알린다(`MinimizedWindowsChanged`, `GetMinimizedWindows`). 셸은 Dock의 최소화 칸에 놓고, 누르면 되돌린다(`RestoreMinimized`).
    - 셸 전용 메서드(최소화한 창 그림, 앱 전환 창, 스크린샷)는 컴포지터가 띄운 셸 프로세스(pid)만 부른다(5.4절의 셸 전용 메서드와 같다). 실행 파일(장치·inode)만 견주면 같은 사용자가 `LD_PRELOAD`를 주고 띄운 bunt-shell도 통과한다.
  - 스크린샷은 렌더 루프가 커서를 뺀 같은 장면을 화면 크기의 텍스처에 따로 그려 읽는다. PNG 저장은 따로 도는 스레드가 한다. 클립보드에는 컴포지터가 선택 영역(image/png)을 내고, 앱이 읽을 때 PNG로 써 준다.
    - 창 찍기(⇧⌘4 뒤 스페이스, ⇧⌘5의 "선택한 윈도우")는 그 창만 따로 그려, 둥근 모서리를 비운 RGBA PNG로 저장한다.
    - 저장 위치와 플로팅 썸네일 보기는 셸이 알린다(`SetScreenshotOptions`). 썸네일을 켜면 저장한 뒤 `ScreenshotSaved(경로)`를 보내 셸이 미리 보기를 띄우고, 끄면 셸의 알림 서버로 알린다.
    - ⇧⌘5 도구 막대는 셸이 그리고, 찍기는 컴포지터에 시킨다(`Screenshot(방식, 타이머)`).
- 입력 소스 전환은 Windows처럼 수정 키만으로도 정할 수 있다(`<Control><Shift>`). 컴포지터는 수정 키를 누르기 시작해 모두 뗄 때까지 다른 키가 없었으면 그 조합의 단축키를 뗀 뒤에 실행한다. 수정 키는 늘 앱에 보낸다
- 앱이 단축키를 막으면(zwp_keyboard_shortcuts_inhibit, 컴포지터가 바로 허락한다) 가상 터미널 전환만 빼고 키를 그대로 보낸다. 시스템 설정은 새 단축키를 적는 동안 이 프로토콜로 ⌘⇥ 같은 키도 받는다.
- 제어 API(`org.buntos.Compositor1`): `GetShortcuts`(id, 분류, 종류, 지금 키, 기본 키, 켬), `SetShortcut(id, 키, 켬)`(켠 다른 단축키와 겹치면 거절), `ResetShortcuts(분류)`, 신호 `ShortcutsChanged`와 `ShortcutActivated(id)`. 키는 GTK 가속기 문자열(`<Shift><Super>3`)이다.
- 에이전트 입력(PressKeys)은 단축키를 거치지 않는다. 에이전트는 리눅스 키(ctrl+c)를 그대로 보낸다.
- 기본 단축키 표와 시트의 모양은 [디자인 스펙](DESIGN-SPEC.md) 9장과 11장에 있다.

### 5.4 세션: 화면 잠금, 로그아웃, 강제 종료

macOS 26의 화면 잠금(⌃⌘Q), 로그아웃(⇧⌘Q), 응용 프로그램 강제 종료(⌥⌘⎋)를 따른다. 모양은 [디자인 스펙](DESIGN-SPEC.md) 4장과 8장에 있다.

- 화면 잠금(ext-session-lock-v1, `comp/src/session_lock.rs`, 잠금 화면 `greeter/src/lock/`):
  - 잠그는 길: ⌃⌘Q, 로고 메뉴의 "화면 잠금", 컴포지터 API `Lock`, logind의 Lock 신호(`loginctl lock-session`), 잠자기 직전(PrepareForSleep).
  - 컴포지터가 먼저 잠근다. 잠그는 순간 모든 화면을 검은 바탕으로 가리고, 앱과 셸에 가던 키보드·포인터 포커스와 잡기(grab)를 거두고, 잠금 화면(`comp.toml`의 `[session] lock`, `bunt-lock`)을 띄운다. 잠금 화면이 화면마다 잠금 표면을 내기 전에도 화면은 이미 가려져 있다. 잠금 화면에는 모든 화면에 잠긴 장면을 낸 뒤에 locked를 보낸다.
  - 잠긴 동안에는 잠금 표면과 커서만 그리고, 키보드는 잠금 표면에만, 포인터는 그 아래 잠금 표면에만 보낸다. 앱 창과 셸(막대, 팝업, 대화 창)은 장면에 넣지 않고, 배경화면은 검은 바탕 아래에 가려진다. 스크린샷(⇧⌘5 도구 막대의 타이머로 기다리던 것 포함)과 창 그림(에이전트)도 하지 않는다.
  - 잠금 프로토콜(`ext_session_lock_manager_v1`)은 컴포지터가 띄운 잠금 화면의 연결에만 보인다. 다른 프로그램은 잠그지도 풀지도 못한다. 잠금 해제(`unlock_and_destroy`)는 컴포지터가 locked를 보낸 잠금 객체에서만 받는다(smithay 0.7은 확인하지 않은 객체의 해제도 받아, 이 메시지를 처리하는 Dispatch를 감쌌다).
  - 잠금 화면이 죽거나 끝나도 잠긴 채로 둔다. 컴포지터가 잠금 화면을 다시 띄운다(0.5초부터 두 배씩 10초까지, 60초 넘게 돌았으면 처음 간격부터). 20초 안에 잠금 표면을 보이지 못한 잠금 화면은 끝내고 다시 띄운다.
  - 푸는 길은 잠금 화면에 사람이 친 암호뿐이다. 잠금 화면은 암호를 PAM(서비스 `bunt-lock`, `common-auth`)으로 확인하고, 맞으면 잠금을 풀고 끝난다. 컴포지터 API에는 잠금 해제 메서드가 없고, logind의 Unlock 신호(`loginctl unlock-session`)도 따르지 않는다.
  - 틀린 암호가 5번이면 30초, 다음부터 1분, 2분, 5분을 기다린 뒤에 다시 받는다(PAM의 실패 지연과 따로). 사람이 키보드로 거듭 칠 때를 늦추는 장치다. 잠금 화면 프로세스 안의 기록이라 잠금 화면이 다시 뜨면 처음부터 센다. 같은 사용자 프로그램은 잠금 화면에 키를 넣을 수 없다(에이전트 입력은 거절하고, 가상 키보드는 입력기에만 연다). pam_faillock은 root로 기록하므로 사용자로 도는 잠금 화면에는 맞지 않는다.
  - 잠금 화면은 뜨자마자 `PR_SET_DUMPABLE`을 끈다. 같은 사용자로 도는 다른 프로그램(AI 도구 포함)이 ptrace로 붙거나 `/proc/<pid>/mem`을 읽어 친 암호를 보거나 암호 없이 잠금을 풀게 만들지 못한다(ssh-agent와 같은 방법).
  - 컴포지터는 특권 클라이언트(셸, 입력기, 잠금 화면)를 이름만 적었으면 세션의 PATH가 아니라 시스템 디렉터리(`/usr/local/bin`, `/usr/bin`, `/bin`)에서만 찾고, 입력기와 잠금 화면에는 PATH도 그 디렉터리로 준다. greetd가 읽는 `~/.profile`은 사용자가 쓸 수 있는 `~/.local/bin`을 PATH 앞에 둘 수 있어, 같은 사용자 프로그램이 그곳에 `bunt-lock`이나 `fcitx5`라는 파일을 두고 원래 프로세스를 끝내면 컴포지터가 다시 띄울 때 그 파일이 잠금 해제나 키보드 잡기를 얻을 수 있었다.
  - 한계: 컴포지터도 그 사용자로 돈다. 커널의 ptrace 제한(Yama `ptrace_scope`)이 0이면 같은 사용자 프로그램이 컴포지터에 붙어 잠금 상태를 바꿀 수 있다. 막으려면 이미지에서 `kernel.yama.ptrace_scope`를 1 이상으로 두거나 컴포지터도 덤프를 끈다(컴포지터의 코어 덤프를 잃는다).
  - 잠긴 동안에도 입력 소스 전환, 가상 터미널 전환, 세션 끝내기(Ctrl+Alt+Backspace)는 듣는다. 세션 끝내기는 잠금을 푸는 것이 아니라 저장하지 않은 앱과 함께 세션을 끝내고 로그인 화면으로 가는 것이다. 잠금 화면이 멈추거나 거듭 죽을 때 사람이 빠져나갈 길로 남긴다.
  - 잠자기: logind에 잠자기 delay 억제(Inhibit "sleep")를 잡아 두고, PrepareForSleep(true)이 오면 잠근 장면을 낸 뒤(3초까지 기다린다) 놓는다. 깨어나면 다시 잡는다. 잠긴 상태는 logind의 LockedHint로도 알린다. logind 연동은 잠금 화면이 설정된 세션에만 켠다.
  - 로그인 화면(`greeter.toml`)에는 잠금 화면이 없으므로 잠그지 않는다.
  - AI 에이전트는 잠긴 동안 아무것도 읽거나 하지 못하고, 잠금 화면도 읽지 못한다(6.3절, 6.5절).
- 로그아웃: 셸의 로그아웃 확인 창(⇧⌘Q, 로고 메뉴의 "<별칭> 로그아웃…")이 60초를 센 뒤 스스로, 또는 [로그아웃]으로 컴포지터의 `LogOut`을 부른다. ⌥⇧⌘Q는 묻지 않고 컴포지터가 바로 한다. 컴포지터는 모든 앱 창에 닫기를 요청하고, 창이 다 닫히면 끝난다. 세션이 끝나면 greetd가 로그인 화면을 다시 띄운다. 10초 안에 닫히지 않는 창(저장할지 묻는 앱)이 있으면 그만두고 알림으로 알린다. 잠긴 동안에는 하지 않는다.
- 응용 프로그램 강제 종료: 셸의 강제 종료 창(⌥⌘⎋, 로고 메뉴의 "강제 종료…")이 컴포지터의 `GetApps`로 창을 가진 앱(pid, 앱 ID, 창 제목, 응답 여부)을 받는다. 응답 여부는 xdg_wm_base 핑에 3초 안에 답했는지다. 고른 앱은 `ForceQuit(pid)`로 SIGKILL을 보낸다. 컴포지터는 그 pid가 창을 가진 앱의 클라이언트인지 확인한다. 컴포지터가 띄운 셸, 입력기, 잠금 화면은 목록에 없고 끝낼 수도 없다.
- 셸 전용 메서드(`LogOut`, `GetApps`, `ForceQuit`)는 컴포지터가 띄운 셸 프로세스(pid)만 부른다. `Lock`과 `GetLocked`(신호 `LockedChanged`)는 세션의 누구나 부른다.
- 셸이 끝나면 컴포지터도 끝나는 설정(`[session] exit-with-shell`): 로그인 화면이 쓴다. 로그인하면 bunt-greeter가 끝나고 컴포지터가 따라 끝나 greetd가 사용자 세션을 연다. 전에는 로그인 화면의 `greeter-shell` 스크립트가 컴포지터에 SIGTERM을 보냈다.
- 빠른 사용자 전환은 하지 않았다. greetd는 VT 하나에서 로그인 화면과 사용자 세션을 차례로 띄우고, 세션이 떠 있는 동안 다른 로그인 화면을 띄우는 길이 없다. 하려면 세션마다 VT를 따로 쓰고(logind의 `SwitchTo`나 VT 전환), 잠긴 세션에서 새 로그인 화면을 띄우는 관리자가 있어야 한다(GDM의 방식).

### 6.1 Aside 설계에서 채택하는 원칙

Aside 공개 자료(aside.com 블로그 "How we built a browser agent...")에서 확인한 설계와 buntOS 대응:

| Aside 원칙/기법 | buntOS 대응 |
|---|---|
| 모델의 학습 데이터 분포를 따른다: 전용 툴셋 대신 Playwright 문법의 JS REPL + bash 두 개만 제공 | 에이전트 API를 **Playwright 로케이터 문법과 동형**으로 설계 (`getByRole`, `getByText`, `click`, `fill`). 별도 학습 없이 모델이 사용 가능. 그리고 OS이므로 bash는 원래 1급 도구 |
| CDP 같은 저수준 프로토콜을 모델에 노출하지 않는다 | Wayland 프로토콜/AT-SPI D-Bus 원시 데이터를 노출하지 않고 고수준 API만 노출 |
| 컨텍스트 윈도 보호: raw DOM 대신 가공된 a11y 트리, ref ID, 중간 노드 제거, 포커스/클릭 가능 여부 추가 | **압축 a11y 스냅샷**: 의미 없는 컨테이너 제거, 상호작용 가능 요소에 ref 부여, 핵심 정보 선두 배치, 크기 상한 |
| 비동기 이벤트를 에이전트에게 신호로 전달 (팝업 열림, 다운로드 시작, 탭 닫힘) | 컴포지터/시스템 이벤트 스트림: 창 생성/종료, 모달 다이얼로그, 알림, 다운로드/프로세스 종료, 권한 요청 |
| 에이전트 탭은 백그라운드에서 열리고 사용자 포커스를 빼앗지 않음 | **에이전트 전용 seat + 오프스크린 출력**: 에이전트가 띄운 창은 사용자 화면을 방해하지 않음. 사용자가 원하면 화면으로 끌어올 수 있음 |
| 뷰포트 1440x900 고정 (CUA 학습 데이터 해상도와 일치) | 오프스크린 출력 해상도는 설정값(기본 1440x900)으로 고정, 사용자 화면 크기와 분리 |
| 비전(CUA)은 DOM 불가 시의 폴백 | 스크린샷+좌표는 최후 폴백. 대상 창 단위 캡처, 좌표는 창 기준으로 매핑 |
| 자격증명은 AI에 노출하지 않고 자동 입력 | Secret Service 연동 **핸들 기반 자동 입력**: 에이전트는 비밀값이 아닌 참조만 받는다. 지금 Secret Service인 gnome-keyring은 앱별 접근 제어가 없어, 세션이 열려 있으면 같은 사용자의 모든 프로세스(사용자 권한으로 명령을 실행하는 AI 도구도)가 D-Bus로 모든 비밀을 읽는다. macOS 키체인은 항목마다 허용 앱이 있다. 핸들 방식과 접근 정책을 설계할 때 함께 푼다 |
| 민감 동작은 사람 승인 | 결제/전송/삭제/권한 상승 등은 **신뢰 레이어 승인 UI** 필요 |
| 모든 접근 기록 | 추가 전용(append-only) 감사 로그 |

2026-10-28에 Aside 스킬로 지금의 Aside가 AI의 브라우저 조작을 어떻게 돕는지 다시 확인했다. Aside CLI 1.26.1028의 `aside guide`, `aside guide repl`, `aside skills`를 읽었고, example.com에서 스냅샷과 diff도 직접 받았다. 블로그 뒤에 드러난 기법과 buntOS 대응은 아래와 같다. 핵심은 도구를 늘리는 것이 아니라 모델이 읽고 행동하는 단위를 바꾸는 것이다.

| Aside에서 확인한 것 | buntOS 대응 |
|---|---|
| `snapshot()`이 트리와 diff를 함께 준다. 처음에는 트리를 읽고, 동작 뒤에는 바뀐 줄만 읽는다 | 스냅샷이 세션과 범위마다 지난 트리를 기억해 unified diff(앞뒤 줄 없음)를 같이 준다 (1단계, 구현) |
| 한 줄에 요소 하나: `- button "New button" [ref=e2] [focused]`. 상호작용 요소만 보기, ref 아래만 보기가 있다. 긴 글은 `…[+736 chars]`로 자르고, 화면 밖 요소와 iframe도 넣는다 | 같은 꼴과 선택지(`-i`, `--ref`). 역할 이름은 ARIA(Playwright)의 것을 쓴다. 웹 페이지에서 스크롤해 가려진 요소는 `[offscreen]`을 달아 넣는다. GTK4 목록은 화면에 보이는 행만 만든다 (1단계, 구현) |
| 같은 요소는 다음 스냅샷에서도 같은 ref다 | 세션이 (앱, 객체 경로)마다 ref를 기억한다 (1단계, 구현) |
| 동작이 요소가 누를 수 있게 되고 화면이 멈출 때까지 기다리며, 필요하면 스크롤한다. 모델은 sleep을 쓰지 않고 새 스냅샷으로 결과를 확인한다 | 동작이 접근성 이벤트가 잠잠해지고 컴포지터가 프레임을 낼 때까지 기다린다. 화면 밖 요소는 Component.ScrollTo로, 그것을 못 하는 앱에서는 휠로 보이게 한 뒤 동작한다 (2단계, 구현) |
| 읽기 단계: 상호작용 트리 → 전체 트리 → 다시 스냅샷 → ref 상자를 그린 스크린샷 → 그냥 스크린샷 | 같은 순서다. 창 단위 캡처에 ref 상자를 그린다 (2·3단계) |
| 행동은 코드(Playwright 문법의 JS REPL)로 한다. 변수가 호출 사이에 남고, 동작과 확인을 한 호출에 묶는다 | `bunt agent repl`(QuickJS 내장)과 MCP의 `repl` 도구 (3단계) |
| 아는 서비스(Slack, Gmail, Notion 등)는 화면을 건너뛰고 로그인된 세션의 자격 증명으로 공식 API를 쓴다. 서비스마다 쓰는 법을 Markdown 스킬로 둔다 | 앱 스킬: 창(컴포지터), 설정(GSettings), 사운드, 네트워크, 앱 실행을 D-Bus·CLI로 다루는 전역 객체와 Markdown 설명 (4단계, 6.2절의 액션 경로) |
| 작업 전체를 브라우저 안의 에이전트에게 맡기고(`aside exec`) 도중에 방향을 바꾼다. 사용자에 대한 기억은 Markdown 파일로 둔다 | 기기 안의 에이전트와 기억은 v0 뒤에 정한다 |
| MCP 도구는 셋뿐이다(exec, repl, browser_profiles) | MCP 도구도 작게 둔다: repl, skills (3단계) |
| 사용자 탭을 가로채지 않는다(열린 탭을 보고 붙는다). 암호는 자동 입력으로 넣는다 | 스냅샷은 읽기만 하고 초점을 옮기지 않는다. 암호 칸의 내용은 읽지 않는다 (1단계, 구현). 동작은 에이전트 seat로 한다 (5단계) |

### 6.2 제어 경로 우선순위

1. **액션 경로**: CLI, D-Bus 인터페이스, 앱이 선언한 인텐트(앱 매니페스트의 `actions`). 가장 빠르고 결정적
2. **의미 경로**: 압축 a11y 스냅샷 + 로케이터 기반 조작
3. **시각 경로**: 창 단위 스크린샷 + 좌표 입력 (폴백)

에이전트는 상위 경로가 가능할 때 하위 경로를 쓰지 않도록 API가 유도한다 (스냅샷에 해당 요소의 액션 경로 존재 여부를 표기).

시각 경로 v0 (2026-10-29): `bunt agent screenshot`이 창 하나를 PNG로 찍고, `click --at x,y`가 그 창 기준 좌표를 누른다(6.4절). 캔버스처럼 접근성 트리에 나오지 않는 UI(후기의 lichess 체스판)와 트리를 내놓지 않는 창에 쓴다.

### 6.3 구성 요소

- `buntd-agent` (시스템 사용자 서비스, Rust)
  - 에이전트 세션 관리, 권한 평가, 감사 로그, 이벤트 스트림
  - 인터페이스: 유닉스 소켓 JSON-RPC (1차), 이를 감싸는 `bunt agent` CLI, MCP 서버 어댑터 (외부 AI 클라이언트 연결용)
- a11y 집계기: AT-SPI 버스 구독, 앱별 트리 캐시, **변경분(diff) 기반 증분 갱신**
- 컴포지터 확장 (`bunt-comp` 내부, 외부 클라이언트에 비공개)
  - 에이전트 seat: 별도 포커스/포인터/키보드. 사용자 입력과 충돌하지 않음
  - 오프스크린 출력: 헤드리스 출력에 에이전트 창 배치
  - 창 단위 캡처: dmabuf 기반, 요청 시에만 인코딩
  - 신뢰 레이어: 승인 다이얼로그는 컴포지터가 직접 그리며, **에이전트 seat의 입력은 신뢰 레이어에 전달되지 않음** (에이전트가 스스로 승인 버튼을 누르는 것을 구조적으로 차단)

v0 구현 (2026-10-29, 1단계 읽기 경로):
- `agent/` 크레이트(`bunt-agent`)가 데몬 `buntd-agent`와 CLI `bunt`를 낸다.
- 데몬은 사용자 서비스다. `buntd-agent.socket`(`$XDG_RUNTIME_DIR/buntos/agent.sock`, 0600)에 처음 붙을 때 뜬다(소켓 활성화). 요청은 한 줄에 하나인 JSON-RPC 2.0이며, `apps`, `installed`, `snapshot`, `launch`, `act`가 있다(`launch`와 `act`는 2단계).
- 접근성 버스는 at-spi2-core가 띄운다. 이 패키지를 이미지에 넣기 전에는 GTK 앱이 접근성 트리를 내놓지 않았다.
- 트리 읽기:
  - GTK4는 누군가 GetChildren으로 물어본 객체만 만든다. 그래서 앱마다 Cache.GetItems로 지금 있는 객체(역할, 이름, 상태, 인터페이스, 부모, 보이는 자식 수)를 한 번에 읽는다.
  - 알려진 자식 수보다 자식이 적은 객체만 GetChildren으로 채우고 목록을 다시 읽는다. 호출은 64개씩 한꺼번에 보낸다.
  - 한 번 채운 부모에 새로 붙는 위젯은 GTK가 바로 만든다. 새 페이지처럼 하위 트리가 통째로 생기면 다음 읽기에서 채운다.
  - 이벤트를 구독하는 캐시는 아직 없다. 읽을 때마다 목록을 다시 받아도 수 ms다(8.3절).
  - GTK4는 더 내놓지 않는 객체(다른 페이지로 넘긴 GtkStack 페이지의 내용)를 목록에 VISIBLE·SHOWING인 채 남기고, 그 부모의 자식 수만 줄여 알린다. 번호가 음수이거나 부모의 자식 수를 넘는 객체와 그 아래는 숨은 것으로 고친다. 루트는 창이 있어도 자식 수를 0으로 알리므로 창은 그대로 둔다. 2차 후기에서 시스템 정보의 파일시스템 탭을 읽으면 숨은 "자원" 페이지의 그래프 글이 수십 줄 먼저 나왔다.
  - 목록이 없는 앱(Firefox의 at-spi2-atk 다리)은 GetChildren으로 트리를 걷는다. Firefox는 웹 페이지 요소의 자리와 동작을 처음 물으면 모른다고(자리 (-1, -1, -1, -1), 동작 0개) 답하고 콘텐츠 프로세스에서 받아 둔다(쓸 때 켜는 캐시). 데몬은 그런 답이면 600ms까지 100ms마다 다시 묻는다. 동작 수는 웹 페이지 안의 요소에만 다시 묻는다. 다른 앱에서는 0개가 참인 답이다.
- 막대·숫자 칸의 값(Value), 글자 칸의 내용(Text), 안내 글과 제목 단계(GetAttributes)는 범위 안에서 보이는 객체만 따로 읽는다. 암호 칸은 읽지 않는다.
- 앱이 호출 하나에 3초 안에 답하지 않으면 그 호출을 오류로 돌린다. 바쁘거나 멈춘 앱 하나가 데몬 전체를 붙잡지 않게 하기 위해서다.
- 기본 범위(활성 창)는 컴포지터가 키보드 포커스를 준 클라이언트의 활성 창이다. 컴포지터 API `org.buntos.Compositor1.GetFocus`가 (pid, 앱 ID나 레이어 이름, 창 제목, 레이어인지)를 준다. GTK의 ACTIVE 상태만 보면 안 된다. 셸의 레이어 창은 팝업(제어 센터)이 닫힌 뒤에도 GTK가 활성으로 알려, 시스템 설정과 함께 두 창이 활성으로 보였다.

v0 구현 (2026-10-29, 2단계 동작 경로):
- 데몬에 `launch`(앱 열기)와 `act`(동작)가 더해졌다. 동작은 접근성 동작을 먼저 쓰고, 키와 포인터는 컴포지터의 에이전트 입력 API로 넣는다.
- 컴포지터 API `org.buntos.Compositor1`의 에이전트 전용 메서드:
  - `GetWindows`: 창마다 pid, 앱 ID, 제목, 자리, 크기, 키보드 포커스
  - `ActivateWindow`, `PressKeys`, `TypeText`, `TextInputActive`, `Click`
  - `Scroll`: 포인터를 그 점으로 옮겨 휠을 돌린다(눈금 수, 한 번에 50눈금까지). 실제 휠과 같은 이벤트다(눈금 하나가 v120 120, 15 논리 픽셀). 시스템 설정의 스크롤 속도와 자연스러운 스크롤은 사람의 장치에만 쓴다. 포인터가 새 표면에 들어가면 100ms 뒤에 그 자리에서 한 번 더 움직이고 돌린 다음 답한다. Firefox는 들어옴(enter) 바로 뒤에 온 휠을 버렸고, 움직임(motion) 뒤의 휠은 받았다(WAYLAND_DEBUG로 확인)
  - `CommitText`: 켜진 글 입력에만 글을 확정하고, 없으면 아무것도 치지 않고 거짓을 돌려준다. 확인과 확정이 이벤트 루프 안에서 한 번에 일어나 그 사이에 포커스가 바뀌어도 키로 새지 않는다
  - `CaptureWindow`, `ClickWindow`: 창 하나만 화면 밖 텍스처에 다시 그려 읽고(스크린샷의 capture_scene, dmabuf가 아니다), 창 기준 좌표를 누른다
- 이 메서드는 buntd-agent만 부른다.
  - 부른 프로세스의 실행 파일을 경로가 아니라 파일(장치·inode)로 `/usr/bin/buntd-agent`와 견준다. 사용자 이름공간에서 다른 파일을 그 경로에 bind mount하면 `/proc/<pid>/exe`의 경로가 같게 보이기 때문이다.
  - 꾸러미 갱신으로 데몬 파일이 바뀌면 옛 데몬은 다음 연결을 받기 전에 끝난다. 소켓에 남은 연결은 systemd가 새로 띄운 데몬이 받는다.
- 입력은 사용자 seat에 실제 입력과 같은 길로 넣는다. 컴포지터 단축키는 거치지 않는다. 에이전트 seat는 5단계다.
- 사람만 답하는 셸 창(관리자 인증 창 `bunt-polkit-agent`, Wi-Fi 암호 창 `bunt-secret-agent`, Bluetooth 페어링 창 `bunt-pairing-agent`. 6.5절)이 떠 있는 동안 컴포지터는 에이전트의 창 활성화, 키, 글, 포인터를 모두 거절한다.
  - 에이전트가 대신 답하거나, 사람이 칠 암호를 다른 창으로 돌리지 못하게 하기 위해서다.
  - 데몬도 이 창을 앱 목록과 스냅샷에서 빼고, 그 안의 요소를 동작 대상으로 받지 않는다. 셸은 레이어 창의 제목(접근성 이름)을 레이어 이름으로 둔다.
- 화면이 잠긴 동안(5.4절) 컴포지터는 에이전트 전용 메서드(창 목록과 창 그림 포함)를 모두 거절한다. 데몬도 요청을 처리하기 전과 뒤에 컴포지터의 `GetLocked`를 보고, 잠겼으면 스냅샷과 모든 동작을 SCREEN_LOCKED(-32003)로 거절한다. 처리하는 사이에 잠겼으면 읽은 것(트리, diff, 스크린샷)을 돌려주지 않는다. 세션 버스에 붙지 못하거나, 컴포지터가 버스에 없거나, 답이 늦는 것처럼 잠긴 상태를 알 수 없으면 잠긴 것으로 본다(앱의 트리는 접근성 버스로 읽히고, 컴포지터의 D-Bus만 멈추고 화면은 잠겨 있을 수 있다). `GetLocked`를 모르는 옛 컴포지터(화면 잠금이 없다)만 잠기지 않은 것으로 본다. 잠금 화면(창 제목 `bunt-lock`)은 앱 목록과 스냅샷에서 빠지고 동작 대상도 되지 않는다.
- 글 치기(`TypeText`):
  - 포커스를 가진 앱이 글 입력(text-input-v3)을 켜 두었으면 입력기가 확정하듯 글을 통째로 넣는다. Wayland 메시지는 4KB를 넘지 못하므로 2KB씩 나눠 확정한다.
  - 한글·이모지도 되고, 입력기가 한글 모드여도 글이 바뀌지 않는다. 키로 치면 한글 모드에서 "hello world"가 "되ㅣㅐ재"로 바뀌었다.
  - 글 입력을 켜지 않은 앱에는 글자마다 키를 친다. 지금 키 배열에 있는 글자만 된다.
  - 데몬의 `type`은 글 입력이 켜지기를 1초까지 기다려 `CommitText`로 넣는다. 안 켜졌고 대상이 글 칸이면 접근성 InsertText로 넣고 다시 읽어 본다. 글자마다 키로 치는 `TypeText`는 `--keys`일 때만 쓴다. 포커스가 빠진 채 키로 치면 글이 문서로 가서 사이트 단축키가 돈다(사용 후기에서 lichess의 `Bxc3+`가 조용히 사라졌다).
  - `fill`과 InsertText 뒤에는 화면이 멈춘 다음 그 칸의 글을 다시 읽어 견준다. 다르면 오류이고, 지금 칸의 글과 `type --ref`를 알린다(후기에서 Firefox 주소창이 "채웠다"고 답하고 비어 있었다).
- 접근성 켜기:
  - Chromium·Electron·Firefox·Qt 앱은 `org.a11y.Status.IsEnabled`가 켜져 있어야 트리를 내놓고, 이 값을 시작할 때 한 번만 본다(Chromium `atk_util_auralinux.cc`의 `ShouldEnableAccessibility`). 데몬이 처음 붙을 때 켜면 그 전에 뜬 앱(AI가 도는 Claude 데스크톱 앱)은 다시 띄워야 한다.
  - 그래서 허용한 AI가 정책에 있으면 컴포지터가 세션을 열 때 `buntd-agent --prepare-session`이 켠다(`comp/data/comp.toml`의 `[session] startup`). 허용한 AI가 없으면 켜지 않는다. 트리를 만드느라 메모리와 CPU를 쓰기 때문이다. 데몬 자체를 로그인 때 띄우지 않는 것은, 컴포지터가 세션 환경(`WAYLAND_DISPLAY`, `LANG`)을 알리기 전에 떠서 데몬이 연 앱이 화면을 열지 못했기 때문이다.
  - 활성 창이 트리를 내놓지 않으면 다른 앱을 대신 읽지 않고 오류로 알리며, `--app`이나 `screenshot`·`click --at`을 권한다. `apps`는 트리 없는 창도 알린다(`untracked`). foot 같은 터미널처럼 접근성을 아예 지원하지 않는 앱은 다시 띄워도 소용없다고 알린다(`unsupported`). 키와 휠은 그런 창에도 간다.
- 앱 열기:
  - 설치된 앱(.desktop)을 지역화된 이름, 번역하지 않은 이름(`Name=`), 데스크톱 ID로 찾는다. 앱 메뉴에 보이는 앱만 다룬다(NoDisplay, OnlyShowIn·NotShowIn).
  - DBusActivatable 앱에는 데몬이 세션 버스로 `org.freedesktop.Application.Activate`를 직접 보낸다. GLib 2.90의 `gio launch`는 이 호출이 앱에 닿기 전에 끝나 버렸다. 그래서 앱(텍스트 편집기)이 서비스 모드로 뜨기만 하고, 창 없이 10초 뒤 끝났다.
  - 나머지는 `systemd-run --user --scope`로 `gio launch`를 띄운다. scope가 없으면 앱이 데몬 서비스의 cgroup에 남아 데몬과 함께 끝난다.
  - 이미 창이 있는 앱은 새로 띄우지 않고 그 창을 앞으로 가져온다(macOS의 `open -a`). 한 인스턴스로 뜨지 않는 계산기가 둘 떠 `--app`이 모호해지던 문제가 없어졌다.
  - 그 앱의 창을 기다린다: 컴포지터에 app_id가 데스크톱 ID(또는 `StartupWMClass`)와 같은 창이 뜨고 접근성 버스에도 그 창이 보여야 한다. 아무 앱의 새 창이나 받던 처음 방식은 늦게 뜬 다른 창을 잘못 돌려줄 수 있었다.
  - 20초까지 기다린다. Activate의 답이 늦어도(포털을 기다리는 앱) 오류가 아니라 아직 창이 없는 것으로 답한다.
  - 연 지 60초가 안 된 앱을 다시 열면 새로 띄우지 않고 그 창을 기다린다. 세션을 막 다시 띄운 VM에서 첫 창이 20초를 넘긴 계산기를 다시 열자 둘이 떴다.
- 컴포지터는 에이전트 요청에 2초 안에 답한다. 소프트웨어 렌더링으로 바쁜 VM에서는 프레임 하나에 수백 ms가 걸려, 처음의 500ms로는 창 목록의 답을 놓쳐 `--app`이 앱을 찾지 못했다.

### 6.4 API 형태

**스냅샷 (v0, 구현).**
- `bunt agent snapshot`은 활성 창을 읽는다. `--app`은 그 앱의 모든 창을, `--ref`는 그 ref 아래만 읽는다.

트리 규칙:
- 이름 없는 panel·filler·scroll pane 같은 그릇은 줄을 만들지 않고 자식을 끌어올린다. 구분선과 스크롤 막대는 뺀다.
- 이름이 없는 요소의 이름은 이렇게 정한다(브라우저의 이름 계산과 같다):
  - 아래에 글이 하나뿐이면 그 글 (단추, 목록 항목)
  - 항목이면 첫 글
  - 글자 칸이면 안내 글
- 반복은 뺀다:
  - 위 줄과 역할·이름이 같은 줄 (메뉴 단추 안의 단추, 단추와 이름이 같은 아이콘)
  - 위 줄과 같은 글
  - 조작 위젯 하나만 든 설정 행은 그 위젯만 남긴다
- 보이지 않는 요소는 뺀다(`--hidden`이면 넣고 `hidden`을 단다).
  - 보이는 웹 페이지 안에서 스크롤해 가려진 요소는 `offscreen`을 달아 넣는다. ref가 있으므로 그대로 누르면 데몬이 먼저 보이게 스크롤한다. 2차 후기에서는 페이지 아래쪽 단추에 ref가 없었다.
  - Firefox와 Chromium은 화면 밖 요소에서 SHOWING만 뺀다. 뒤쪽 탭의 문서는 문서 자신이 보이지 않으므로 그 아래는 뺀다. 웹 문서 밖에서 VISIBLE만 있는 요소는 GTK3의 다른 탭 페이지처럼 숨은 것이라 뺀다.
- 한 번에 2000줄까지 내고, 넘으면 ref로 나눠 읽으라고 적는다.
- 웹 페이지의 글: Firefox는 그릇(문단, div, 목록 항목, 칸)에 바로 든 글을 자식으로 내놓지 않고 그릇의 Text에 넣으며, 자식 요소가 든 자리에 U+FFFC를 둔다. 데몬은 그릇의 글을 읽어 그 자리에 자식을 끼워 화면의 차례대로 `text:`와 요소를 낸다. 자리 수와 자식 수가 다르면 글을 먼저 낸다. U+FFFC는 이름과 값에서 뺀다. Firefox는 창과 문서에도 EditableText를 붙이므로 EDITABLE 상태가 있어야 글자 칸으로 본다. 2차 후기에서는 검색 결과의 본문이 빠지고 창의 `value=`가 U+FFFC로 찼다.
- 상태와 값: `hidden`, `offscreen`, `active`, `focused`, `checked`, `mixed`, `pressed`, `selected`, `expanded`/`collapsed`, `disabled`, `readonly`, `secret`(암호 칸), `required`, `invalid`, `value=`, `range=`, `placeholder=`, `level=`, `description=`.
- 글을 쓰는 콤보 상자(Firefox 주소 막대)도 글자 칸처럼 `value=`를 낸다.

**동작 (v0, 구현).**
- `bunt agent launch <앱>`: 앱을 열고 새 창의 상호작용 요소 트리를 낸다. 이미 열려 있으면 그 창을 앞으로 가져와 그 트리를 낸다. `apps --installed`는 열 수 있는 앱 목록이다.
- `click <ref> [--pointer]`, `fill <ref> <글>`, `set <ref> <값>`, `focus <ref>`, `select <ref>`
- `press <키…> [--ref <ref>]`: `ctrl+a BackSpace`, `Return`처럼 띄어 쓴 키들. 수정 키는 ctrl, shift, alt(option), super(cmd)다. `--ref`는 누를 때마다 그 요소에 포커스를 다시 주므로 Tab은 늘 그 요소에서 시작한다. `--keep-focus`는 그 창만 앞으로 가져오고 창 안의 포커스는 그대로 둔다(Tab으로 양식 지나가기).
- `type <글> [--ref <ref>] [--keys] [--keep-focus]`: 글 칸에 포커스가 없으면 아무것도 치지 않고 오류다. `--keys`는 글 입력이 없을 때 키로 쳐도 된다는 뜻이다(글 칸 없이 키만 받는 게임 등).
- `scroll <ref>`: 그 요소가 화면에 들어오게 스크롤한다. `scroll <up|down|left|right> [<눈금>] [--ref <ref>]`: 그 요소(스크롤할 목록이나 문서)의 보이는 가운데, 없으면 창 가운데에서 휠을 돌린다(기본 5눈금).
- `screenshot [--app <앱>] [--out <파일>]`: 창 하나의 PNG 경로를 낸다. `click --at x,y [--app <앱>]`: 그 창 기준 좌표를 누른다.
- `--app`: ref가 없는 동작(`click --at`, `press`, `type`, `scroll`)은 그 앱의 창에 한다. ref와 함께 쓰면 ref가 그 앱의 것인지 보고, 다르면 `--app`을 빼라고 알린다. 2차 후기에서는 도움말이 모든 동작의 선택지로 적었는데 `click <ref> --app`을 거절했다.
- 동작마다 `--settle <ms>`(기본 3000, 0이면 바로 한 번 읽는다)로 기다림 상한을 고른다. 답의 `settled`가 거짓이면 상한까지 바뀌고 있던 것이다(접속자 수가 늘 바뀌는 페이지).
- 답에는 한 일, 화면이 멈추기까지 걸린 시간, 그 창 트리의 diff가 있다. 새 창이 떴으면 그 제목도 적는다. 동작과 확인이 호출 하나로 끝나 스냅샷을 따로 다시 읽지 않아도 된다(Aside와 같다).

동작 규칙:
- 누르기:
  - 접근성 동작을 click, press, toggle, activate, jump, open 차례로 찾는다. GetActions는 지역화한 이름("토글")을 주므로 동작 수와 GetName으로 지역화하지 않은 이름을 읽는다.
  - 동작이 없는 목록 항목은 부모 목록의 SelectChild로 고른다. 그것도 없으면 포인터로 요소 가운데를 누른다.
  - 포인터로 누르기 전에는 그 창을 앞으로 가져온다. 가려진 창을 누르면 위에 있는 창이 눌리기 때문이다.
- 채우기는 EditableText.SetTextContents다. 암호 칸은 채우지 않는다. 값은 Value.CurrentValue를 쓴다(막대, 숫자 칸).
- 포커스:
  - GTK4는 접근성의 GrabFocus를 지원하지 않는다(NotSupported). 그래서 글 칸은 사람처럼 포인터로 눌러 포커스를 주고 커서를 글 끝으로 옮긴다(Text.SetCaretOffset).
  - 다른 요소는 누르면 동작이 일어나므로 누르지 않고, 누를지 정하라고 오류로 답한다. 이미 포커스가 있으면 아무것도 하지 않는다.
- 키·글:
  - ref가 있으면 그 창을 앞으로 가져와 요소에 포커스를 준 뒤 한다(위와 같은 방법). 그러지 않으면 폼의 둘째 칸에 칠 글이 포커스가 있던 첫 칸에 들어간다.
  - 글 칸이면 그 칸이 글 입력을 켤 때까지 1초까지 기다린다. 켜지 않으면 접근성으로 커서 자리에 넣는다(EditableText.InsertText). 포털을 기다리느라 바쁜 앱이 글 입력을 늦게 켜 키로 쳐졌던 일이 있었다.
- 자동 대기:
  - 50ms마다 그 창을 다시 읽는다. 바뀐 뒤 150ms 그대로면 멈춘 것이다.
  - 바뀌지 않으면 1초까지 기다리고, 어떤 경우든 3초에서 멈춘다.
  - 처음에는 "두 번 읽어 같으면 멈춤"이었는데, 계산기처럼 결과를 늦게 그리는 앱에서 결과를 놓쳤다.
  - 보이는 요소가 불러오는 중(BUSY, 페이지를 받는 문서)이면 멈춘 것으로 보지 않고 `--settle` 상한까지 기다린다. 2차 후기에서 주소 막대에 검색어를 넣고 Return을 누르면 결과가 뜨기 전에 513ms로 끝났다. 2.5초 걸리는 페이지에서는 2.9초를 기다려 그 페이지를 읽는다.
- `--app`은 이 차례로 찾는다: 접근성 이름, 설치된 앱의 이름·데스크톱 ID(같은 것, 없으면 일부가 맞는 하나. 컴포지터 창의 app_id로 잇는다), 창 제목, 이름이나 제목의 일부. `--app calc`, `--app editor`도 된다.
- 스크롤:
  - 화면 밖 요소(`offscreen`)는 동작 전에 사람처럼 먼저 보이게 스크롤한다. 앱이 하면(Component.ScrollTo, Firefox) 그것을 쓰고 1초까지 SHOWING을 기다린다. 못 하면(GTK4는 NotSupported) 창 가운데에서 요소 쪽으로 휠을 돌리며(멀수록 많이, 한 번에 5눈금까지) 다시 본다. 30번까지 하고, 요소가 더 움직이지 않으면 멈춘다.
  - Firefox에서는 자리를 받아 두기 전에 한 ScrollTo가 페이지를 움직여도 SHOWING을 고치지 않아 휠로 다시 찾았다. 그래서 ScrollTo 앞에 그 요소의 자리를 먼저 묻는다.
  - GTK4 목록(GtkListView, GtkColumnView)은 화면에 보이는 행만 만든다. 화면 밖 행은 트리에 없으므로 목록에 휠을 돌리고 다시 읽는다(파일 앱의 `/usr/bin`에서 휠 10눈금에 행이 바뀐 diff가 나온다). GTK4의 GtkTreeView(시스템 정보의 프로세스 목록)는 행을 접근성으로 내놓지 않는다.
- 앱을 끝내는 동작: 동작 뒤 앱이 끝나면(계산기 닫기, 문서 버리기) 실패가 아니라 그 일을 알린다(`…; then the app quit (window "계산기" closed)`). 창만 닫히면 `then its window closed`다. 2차 후기에서는 D-Bus 오류(`ServiceUnknown`)가 그대로 보여, AI가 된 동작을 실패로 알고 되풀이할 수 있었다.
- 오류 번호(JSON-RPC): -32000 접근성 버스·앱의 오류, -32001 허용하지 않은 클라이언트나 인증 창, -32002 사용자가 막은 앱(6.5절), -32003 화면이 잠김(5.4절. 사람이 암호로 풀 때까지 기다리라고 알린다).

### 6.5 권한 모델

- 권한 단위: `(에이전트, 대상 앱, 동작 등급)`
- 동작 등급: `read`(스냅샷/캡처) / `interact`(입력) / `sensitive`(전송, 삭제, 결제, 비밀값 사용) / `system`(sudo, 패키지 설치, 서비스 제어)
- `sensitive`, `system`은 기본적으로 매번 신뢰 레이어 승인. 정책은 TOML로 사용자가 조정
- 에이전트 프로세스는 별도 cgroup slice와 사용자 네임스페이스에서 실행

v0 구현 (2026-10-29, 접근 정책):
- 무엇을 정하는가:
  - 시스템 설정 > AI 에이전트에서 이 컴퓨터를 제어할 수 있는 AI(켬·끔)와 AI가 접근할 수 없는 앱을 정한다.
  - 정책은 `/etc/buntos/agent-access.toml`(root:root 0644)이다. 고치는 것은 `bunt-access-helper`다.
  - 도우미는 pkexec로 root로 돈다. polkit 동작은 `org.buntos.agent.access.change`이고 기본값이 auth_admin이라 바꿀 때마다 관리자 암호를 묻는다.
  - auth_admin_keep으로 두지 않는다. 인증한 뒤 몇 분 동안 같은 세션의 허용받은 AI가 남은 인증으로 제 권한을 늘릴 수 있기 때문이다.
- 클라이언트를 알아보는 법(`bunt-access`의 identify):
  - 데몬은 연결마다 SO_PEERCRED의 pid로 클라이언트를 알아보고, 요청마다 정책을 다시 읽는다. 설정에서 바꾼 것이 데몬을 다시 띄우지 않아도 바로 듣는다.
  - 소켓에 붙은 프로세스에서 부모로 올라가며 처음 나오는 진짜 프로그램을 고른다. 셸, env·sudo 같은 감싼 프로그램, bunt CLI는 건너뛴다.
  - node·python 같은 인터프리터면 실행한 스크립트 경로까지 맞춘다. 실행 파일과 스크립트 경로가 모두 같아야 같은 AI다.
  - 요청한 프로세스나 그 사이의 셸·sudo가 root로 돌면 관리자이고, 관리자는 늘 허용한다(직렬 콘솔과 e2e의 `sudo -u buntos bunt`).
    - 사용자로 도는 데몬은 root 프로세스의 실행 파일 경로를 읽지 못한다. 그래서 root 프로세스는 `/proc/<pid>/status`의 이름으로 감싼 프로그램인지 본다. root 프로세스의 이름은 사용자가 바꾸지 못한다.
  - login·sshd가 띄운 사용자 셸 아래는 관리자가 아니다.
- 받지 않은 요청과 막은 앱:
  - 허용되지 않은 AI의 요청은 거절하고 `~/.local/state/buntos/agent-requests.toml`에 남긴다. 설정의 [+]가 이 목록을 보여 준다.
  - 셸이 이 기록을 지켜보다가 방금 거절된 AI를 한 번 묻는다(AI 접근 요청 창, `shell/src/agent_access.rs`). macOS가 손쉬운 사용 권한이 없는 앱에 "이 컴퓨터를 제어하려고 합니다"라고 묻는 경고를 따른다.
    - 묻는 요청: 10분 안에 붙었고, 아직 묻지 않았고, 정책 목록에 없는(켠 것도 끈 것도 아닌) AI다(`bunt_access::request_to_ask`). 물은 때를 기록의 `asked`에 남겨 같은 프로그램은 다시 묻지 않는다. 데몬과 셸이 같은 기록을 고쳐 쓰므로 옆의 잠금 파일을 잡는다.
    - [시스템 설정 열기]는 `bunt-settings agent --add-client <실행 파일> [--script <스크립트>]`로 AI 에이전트 페이지의 추가 시트를 그 AI를 고른 채로 연다. 목록에 이미 있으면 그 줄을 고른다. 사용자가 [추가]를 누르면 인증 창이 관리자 암호를 묻는다. 허용은 늘 사람이 한다.
    - [거부]와 Esc는 창만 닫는다. 창은 인증 창과 같은 레이어 이름(`bunt-polkit-agent`)을 써서, 컴포지터와 데몬이 에이전트가 이 창을 건드리지 못하게 막는다. AI가 띄우는 창이라 키보드는 창을 눌렀을 때만 받는다(다른 앱에 글을 치다 Return으로 잘못 고르지 않게).
    - 데몬의 거절 문구가 AI에게 사용자가 할 일을 알린다. 처음이면 "buntOS가 지금 묻고 있으니 경고에서 \"Open System Settings\"와 \"Add\"를 골라 달라고 하라", 이미 물었으면 "사용자가 이미 물음을 받았다", 목록에서 꺼 둔 AI면 "사용자만 다시 켤 수 있다"이다(`Refusal`).
  - 막은 앱은 데스크톱 ID(= Wayland app_id)로 적는다. 데몬은 컴포지터 창의 app_id로 그 앱의 pid를 찾는다.
  - 막은 앱은 `apps`와 `apps --installed`에서 빠진다. 그 앱의 스냅샷, 동작, 열기는 BLOCKED_APP(-32002)으로 실패한다. 막기 전에 받은 ref로 하는 동작도 실패한다.
- 사람의 권한과 인증 창:
  - 이미지에는 정규 계정이 없고, 처음 켤 때 만든 계정이 관리자(sudo 그룹)다. sudo와 polkit 관리 작업은 그 계정의 암호를 묻는다(Debian polkit의 관리자 = sudo 그룹). 에이전트의 `system` 등급 동작도 이 인증을 거친다.
  - 세션의 polkit 인증 에이전트는 bunt-shell이다(macOS 인증 창 모양, [디자인 스펙](DESIGN-SPEC.md)).
  - polkit 128은 `polkit-agent-helper-1`을 setuid 없이 소켓 활성화(`/run/polkit/agent-helper.socket`)로 root로 띄운다. 인증 에이전트는 그 소켓에 사용자 이름과 쿠키를 쓰고 PAM 물음에 답한다.
  - 에이전트는 인증 창을 읽지도 조작하지도 못한다(6.3절).
  - 화면 잠금(5.4절): 잠긴 동안 에이전트는 아무것도 읽거나 하지 못하고, 잠금 화면도 읽지 못한다. 잠금을 푸는 길은 사람이 잠금 화면에 친 암호뿐이다. 컴포지터 API에 잠금 해제 메서드가 없다.
  - Wi-Fi 암호와 Bluetooth PIN·확인 번호도 사람만 답한다. 세션의 NetworkManager 비밀 에이전트(`shell/src/secret_agent.rs`)와 BlueZ 기본 페어링 에이전트(`shell/src/pairing_agent.rs`, 능력 KeyboardDisplay)가 bunt-shell이다.
    - 창은 인증 창과 같은 틀이고 레이어 이름이 `bunt-secret-agent`, `bunt-pairing-agent`다. 컴포지터(`comp/src/agent.rs`의 `AUTH_NAMESPACES`)와 buntd-agent(`agent/src/atspi.rs`의 `HUMAN_ONLY_WINDOWS`)가 같은 목록으로 이 창들을 막는다.
    - 사람이 고르지 않은 때 뜨는 창은 키보드를 바로 가져가지 않는다. Wi-Fi 암호 창은 메뉴 막대에서 사람이 방금 고른 네트워크일 때만 키보드를 독점하고, 그 밖의 창과 Bluetooth 페어링 창(상대 기기가 먼저 청할 수 있다)은 눌러야 받는다. 다른 앱에 치던 글이 이 창으로 가지 않게 하기 위해서다. NetworkManager의 USER_REQUESTED는 D-Bus로 연결을 켠 프로그램이면 어느 것이든 붙으므로 믿지 않는다: 같은 세션의 프로그램이 제 연결(사용자 소유, 비밀 저장)을 켜 창을 띄우면, 키보드를 가져간 창에 사람이 친 글이 그 연결에 저장되고 그 프로그램이 다시 읽을 수 있다.
    - Bluetooth 서비스 허용(AuthorizeService)은 이번 연결만이다. 믿는 기기(Trusted)로 두면 그 기기의 다른 서비스(키보드 입력 등)도 묻지 않고 붙는다.
    - 에이전트는 NetworkManager·bluetoothd가 아닌 호출을 거절한다. 받은 비밀은 기록에 남기지 않고, 답한 뒤 메모리를 지운다.
    - NetworkManager는 받은 암호를 모든 사용자의 연결에 저장하기 전에 에이전트의 `org.freedesktop.NetworkManager.settings.modify.system` 권한을 본다(upstream 기본값 auth_admin_keep). Debian의 정책에 따라 관리자 인증 창이 먼저 뜰 수 있다.
  - 비밀 저장소(Secret Service)는 gnome-keyring이다. libpam-gnome-keyring이 pam-auth-update로 `common-auth`·`common-session`에 들어가므로, greetd 로그인의 암호로 login 키링을 열고 처음이면 만든다(macOS 로그인 키체인). 앱이 비밀을 저장할 때 따로 키링 암호를 묻거나 켤 때마다 잠금 해제 창이 뜨던 것이 없어졌다. 시스템 설정이 `passwd`로 암호를 바꾸면 키링 암호도 따라간다. Flatpak 앱은 Secret 포털(gnome-keyring 구현)로 같은 키링을 쓴다.
  - 세션의 `XDG_CURRENT_DESKTOP`은 `buntOS:GNOME`이다(앞이 우선인 목록, 세션 스크립트 `/usr/libexec/buntos/session`이 정한다). Electron 앱(Claude 데스크톱 앱 등)의 safeStorage는 이 목록에 GNOME·KDE·XFCE처럼 아는 데스크톱이 있어야 비밀 저장소로 키링(libsecret)을 고르고, 없으면 키링이 있어도 평문(`basic_text`)에 저장한다. `buntOS`만 두었을 때 Claude 앱이 "시스템 키링을 사용할 수 없습니다"라고 알렸고 로그인 토큰을 남기지 못했다(2026-10-29, 앱 로그 `backend=basic_text`). 우분투의 `ubuntu:GNOME`과 같은 방식이다.
    - Chromium 156(Debian)은 모르는 데스크톱이면 Secret 포털(우리 설정으로 gnome-keyring)을 써서 이미 키링에 저장했다(`Local State`의 `os_crypt.portal`). Electron의 safeStorage에는 이 길이 없다.
    - buntOS가 먼저라 포털은 `buntos-portals.conf`(GTK 구현)를 그대로 쓴다. 세션이 XDG 자동 시작을 돌리지 않으므로 GNOME 전용 자동 시작 항목(gnome-keyring, localsearch)도 뜨지 않는다. 로그인 화면 세션은 `buntOS` 그대로다.
    - 입력기(fcitx5)에는 `buntOS`만 준다(`comp.toml`의 `[session] input-method`). fcitx5는 이 목록에 GNOME이 있으면 GNOME 셸로 알고, 입력기 팝업을 보이려면 셸 확장(kimpanel)을 깔라고 알림을 띄웠다. GNOME 셸은 입력기 프로토콜을 열지 않아 그 확장이 팝업을 그려야 하지만, buntOS는 컴포지터가 input-method-v2로 팝업을 글자 커서 아래에 띄우므로 맞지 않는 안내였다.
    - fcitx5가 다른 환경으로 떠도(터미널에서 띄우기 등) 그 안내가 사용자를 헷갈리게 하지 않도록, fcitx5의 Wayland 진단 알림(GNOME 셸 확장, KWin, 입력 모듈 환경 변수 안내) 셋을 기본 설정 `/etc/xdg/fcitx5/conf/notifications.conf`의 `HiddenNotifications`로 감춘다. 알림의 "다시 표시 안함"이 쓰는 목록과 같다. 사용자의 `~/.config/fcitx5`에 같은 파일이 생기면 그쪽이 앞선다.
- 한계와 다음 단계:
  - 데몬이 지키는 정책이다. 같은 사용자로 도는 AI가 접근성 버스에 직접 붙으면 막지 못한다.
  - 경로로 알아보므로, 허용한 프로그램을 실행할 수 있는 프로그램은 그 권한을 얻는다.
  - 스스로 업데이트하는 AI(Claude 데스크톱 앱 Code 탭의 `~/.config/Claude/claude-code/<판>/<해시>/claude`, 네이티브 CLI의 `~/.local/share/claude/versions/<판>`)는 판마다 경로가 바뀐다. 도우미가 더할 때 홈 아래 경로의 판 번호·빌드 해시 자리를 `*`로 바꾼 패턴도 적어(`bunt_access::version_pattern`), 업데이트해도 허용이 풀리지 않는다. 홈부터 그 디렉터리까지 그 사용자나 root만 쓸 수 있을 때만 만든다. 시스템 경로는 정확히 비교한다.
  - 인증 창은 같은 사용자의 셸이 그리므로, 다른 같은 사용자 프로그램이 비슷한 가짜 창을 그릴 수 있다.
  - 단단한 격리는 5단계(에이전트 seat, 샌드박스, 컴포지터가 그리는 신뢰 레이어)다.

### 8.2 컴포지터/셸

- 데미지 트래킹: 변경 영역만 재합성. 버퍼 전체를 손상으로 알리는 SHM 앱(GTK의 cairo 렌더러)은 앞 커밋과 타일로 견주어 바뀐 곳만 남긴다
- 다이렉트 스캔아웃: 전체화면/단일 창은 합성 생략. 앱 버퍼(dmabuf)의 스캔아웃은 아직 켜지 않았다. 흐림이 화면 버퍼를 복사하므로, 평면에 따로 올린 창과의 순서를 하드웨어에서 확인한 뒤 켠다
- dmabuf 제로카피 경로 우선: 컴포지터가 GPU로 그리면 linux-dmabuf v5를 연다. 기본 피드백은 컴포지터가 그리는 GPU의 렌더 노드(EGL이 알리는 장치. 화면 장치와 GPU가 다른 SoC에서는 Mesa kmsro가 짝지은 GPU, 예: mediatek-drm과 Panthor)와 렌더러가 텍스처로 읽는 형식이다. 앱 버퍼는 만들 때 렌더러로 가져와 보고, 가져온 텍스처를 그릴 때 다시 쓴다(복사 없음)
- 앱의 그리기 방식은 컴포지터가 자기 GL 렌더러를 보고 정한다(`comp/src/gpu.rs`). 렌더러는 화면 GPU에 EGL을 만들어 봐야 알기 때문이다
  - CPU 렌더러(llvmpipe, softpipe, SwiftShader): 띄우는 프로그램과 D-Bus 활성화·systemd 사용자 환경(prepare의 `dbus-update-activation-environment --systemd`)에 `GSK_RENDERER=cairo`를 주고 linux-dmabuf를 열지 않는다. GTK의 GL·Vulkan은 소프트웨어 래스터라이저에서 메모리를 몇 배 쓴다(시스템 설정이 GL로 475MB, cairo로 102~164MB, [개발 환경](../dev/environment.md) 7장)
  - GPU: GTK가 Vulkan이나 GL을 골라 dmabuf로 보낸다. linux-dmabuf를 열지 못하면(렌더 노드나 렌더러가 읽는 형식이 없다) CPU 렌더러처럼 다룬다
  - 가상 GPU(virgl): 앱이 virgl 드라이버로 그리므로 GPU로 다룬다. 호스트가 CPU로 그리면(`virgl (llvmpipe …)`) 프레임 수만 CPU 렌더러처럼 줄인다(60Hz, 뒤의 창 30Hz)
  - 세션이 정한 `GSK_RENDERER`는 그대로 물려준다(시험할 때)
- 흐림(유리, [디자인 스펙](DESIGN-SPEC.md) 2.2절): 셸 유리와 앱이 ext-background-effect-v1로 요청한 영역만 흐리고, 아래 장면이 흐릴 곳에 닿게 바뀐 프레임에만 다시 흐린다. 흐려 둔 결과는 표면과 화면마다 둔다
  - 손상 추적은 불투명한 요소 아래를 그리지 않으므로, 흐림 위의 요소(흐릴 표면 자신 포함)는 흐릴 범위에서 불투명 영역을 빼고 알린다. 흐릴 곳이 위 요소에 다 가려지면 흐리지 않는다(다 가려진 창은 보이지 않는 표면으로 남아 프레임 알림이 줄어든다)
  - 앱이 보낸 영역은 펴는 도중의 조각이 64개를 넘으면 감싸는 사각형 하나로 흐린다(요청 하나의 일을 묶는다)
- 프레임 루프에서 힙 할당 금지: 버퍼/정점/명령 리스트는 풀(pool)과 프레임 아레나로 재사용
- 오프스크린 출력은 에이전트 세션이 있을 때만 생성하고, 관찰자(스냅샷/캡처 요청)가 없으면 렌더링 빈도를 낮춤
- 애니메이션은 디스플레이 vblank 동기화, 주사율은 KMS 모드 목록에서 읽음(하드코딩 금지)

### 8.3 Agent Control Plane

- a11y 트리: 앱별 캐시 + 변경 이벤트 기반 증분 갱신. 전체 재수집은 캐시 무효화 시에만
- 실측 (2026-10-29, arm64 QEMU, v0는 이벤트 캐시 없이 읽을 때마다 GetItems):
  - 시스템 설정: 첫 스냅샷 16ms(객체 121개를 GTK가 새로 만드는 시간 포함), 이후 3~5ms
  - 셸: 처음 8ms, 이후 2ms
  - 텍스트 편집기: 9ms(객체 84개, 10줄)
- 동작 실측 (2026-10-29, 같은 VM):
  - 글 칸 채우기·글 치기와 스위치: 화면이 멈추기까지 210~220ms(바뀐 뒤 그대로 150ms를 포함)
  - 계산기 `=`: 430~530ms(결과를 늦게 그린다)
  - 바뀌는 것이 없는 키(Escape): 1초를 기다려 "바뀐 것 없음"으로 답한다
  - 앱 열기: 떠 있는 앱은 0.3초 안, 처음 여는 앱은 0.5~5초(포털이 늦을 때 더)
  - 계산기에서 6 × 7을 계산해 결과를 읽고 텍스트 편집기에 쓰는 시나리오 전체: 4.3초(두 앱 열기 포함)
- 스냅샷 직렬화: 스트리밍 직렬화, 크기 상한 초과 시 하위 트리를 요약 노드로 대체
- 캡처: 요청 시에만 GPU에서 다운스케일 후 인코딩. 상시 캡처 금지
- 감사 로그: 메모리 버퍼 + 주기적 flush, 크기 기반 로테이션

### 8.4 초기 예산 (가설, Phase 1에서 실측 후 확정)

| 항목 | 초기 예산 |
|---|---|
| 로그인 직후 유휴 시스템 메모리 (셸+컴포지터+서비스) | 측정 기준선 확보 후 결정. 비교 대상: 동일 기기 ZUI 16 유휴 사용량, Debian+GNOME 유휴 사용량 |

## 9. 테스트 전략 (규칙 2, 3)

### 9.1 원칙

- 테스트를 위한 테스트 금지: 커버리지 수치를 목표로 삼지 않는다. 각 테스트는 "깨지면 사용자 기능이 깨지는" 동작을 검증해야 한다
- 함수/아키텍처 변경: 해당 단위 테스트 필수 (Rust `cargo test`, 셸 스크립트는 bats)
- main 병합 전: e2e 필수

### 9.2 e2e 구성

- 대상: x86-64 QEMU, aarch64 QEMU(`virt`, UEFI) **두 아키텍처 모두 동일 시나리오**
- 구동 방식: 빌드된 이미지를 QEMU로 부팅 → 시나리오 실행 → 결과 수집
- **e2e 드라이버로 buntOS 자체의 Agent Control Plane을 사용** (도그푸딩). 별도의 테스트 전용 자동화 경로를 만들지 않으므로 테스트 코드가 실제 제품 경로를 검증한다
- Agent Control Plane이 준비되기 전의 e2e 드라이버 (ADR-009)
  - Phase 0: QEMU 시리얼 콘솔(로그인, 명령 실행) + QMP(`input-send-event`로 키 입력, `screendump`) 임시 드라이버로 부팅 → 셸을 검증한다
  - Phase 1: Agent Control Plane 최소판(`buntd-agent` JSON-RPC, 실행 경로, AT-SPI 읽기 경로)을 앞당겨 구현한다. 키 입력은 QMP로 넣어 가상 키보드 → 컴포지터 → fcitx5 → 앱으로 이어지는 실제 입력 경로를 거치게 하고, 값 확인은 AT-SPI 읽기로 한다
  - 읽기 경로가 들어간 뒤(2026-10-29) e2e 1번은 콘솔 셸에 이어 그래픽 셸이 떴는지를 `bunt agent snapshot --app bunt-shell -i`로 본다. 누를 수 있는 요소(메뉴 막대 항목, Dock 단추)가 10개 이상이어야 한다. 자체 컴포넌트를 넣지 않은 이미지에서는 건너뛴다
  - 2026-10-29부터 e2e 1번은 시험 계정을 systemd 자격 증명으로 넘겨(`-smbios type=11,value=io.systemd.credential:buntos.account=buntos:buntOS:buntos`) 부팅하고, 로그인 화면(bunt-greeter가 저널에 `ready (login)`을 남긴다)에 QMP로 암호를 친다. 세션이 뜨지 않으면 세 번까지 다시 친다. 들어간 뒤 `sudo -n`이 암호를 요구하는지 확인한다
  - e2e 5번(2026-10-29, `tests/e2e/agent-apps.sh`)은 같은 부팅에서 e2e 1번에 이어 돈다. 에이전트만으로 계산기에서 6 × 7을 계산해 결과를 읽고, 텍스트 편집기에 채운 뒤 입력기를 한글 모드로 두고 글을 더 친다. 시스템 설정 사이드바도 누른다. 열기, 값, 다시 열기, 한글 모드, 편집기의 글, 설정 페이지를 본다. 사용 후기를 반영한 뒤로는 창 스크린샷과 창 기준 좌표 누르기(계산기의 `=`, Firefox의 캔버스), fill이 칸에 남지 않으면 오류인지, 글 칸이 아닌 곳의 type을 거절하는지도 본다. 2차 후기를 반영한 뒤로는 ref와 `--app`, 닫기 단추가 앱을 끝냈다는 답, 시스템 정보의 숨긴 탭 페이지, 긴 웹 페이지의 글 차례와 U+FFFC, 화면 밖 단추의 `offscreen`, 휠 스크롤, 화면 밖 단추를 스크롤해 누르기도 본다. e2e 1번은 허용한 AI가 있으면 세션을 열 때 접근성이 켜지는지 본다
  - e2e 6번(2026-10-29, `tests/e2e/shortcuts.sh`)은 e2e 5번에 이어 돈다. 키는 QMP로 가상 키보드에 넣어 실제 입력과 같은 길(libinput → 컴포지터 단축키 → 입력기 → 앱)을 거치게 하고, 결과는 에이전트와 컴포지터 API로 읽는다. 텍스트 편집기에서 ⌘A·⌘C·⌘→·⌘V·⌘Z·⌥⌫, ⌘⇥ 앱 전환, ⌘M 최소화와 돌아오기, ⌘스페이스 모든 앱, ⇧⌘3 스크린샷, 단축키 API, 터미널(foot)에서 ⌘V로 붙여 실행하기와 ⌘W로 닫기, 입력 소스 전환을 ⌃⇧로 바꿔 눌렀다 떼기를 본다. 2026-10-30부터는 창의 최소화 단추와 Dock의 최소화 칸에서 돌아오기, ⌘를 누른 채 ⇥를 누를 때의 앱 전환 창과 ⌘를 뗄 때의 전환(QMP로 ⌘를 따로 누르고 뗀다), 스크린샷 미리 보기, ⇧⌘5 도구 막대도 본다
  - e2e 4번(2026-10-30, 한글 입력, `tests/e2e/hangul.sh`)은 e2e 6번에 이어 돈다. 키는 QMP로 넣어 libinput → 컴포지터 → fcitx5(input-method-v2, fcitx5-hangul) → 앱(text-input-v3)의 실제 길로 조합하게 하고, 결과는 에이전트(앱의 글)와 입력기 상태(fcitx5)로 읽는다. e2e 5번은 에이전트의 글 입력으로 확정해 조합을 거치지 않는다. 기대값은 macOS 한국어 2벌식과 fcitx5-hangul의 기본 동작이다. 본다:
    - 입력 소스 전환: ⌃스페이스와 한/영 키(QEMU `lang1` → evdev KEY_HANGEUL → keysym Hangul)로 바뀌고 메뉴 막대의 입력 소스 표시가 fcitx5와 같다. 글 입력 칸 밖(사이드바 항목)에 포커스가 있어도 바뀐다. GTK4 앱은 글 입력 칸 밖에서도 입력기를 켜 두어(치면 검색을 여는 앱에 한글로 친다) 입력기의 키보드 잡기가 아니라 포커스로 본다
    - 텍스트 편집기의 2벌식 조합: 안녕하세요, 쌍자음(⇧R·⇧T), 겹모음(ㅘ, ㅢ), 받침 넘김(각 + ㅏ → 가가), 조합 중 Backspace(한 → 하), 조합 중 스페이스·문장 부호, 확정한 글자의 Backspace, 왼쪽 Shift만 눌렀다 떼기
    - 조합 중 ⌃스페이스·한/영 키, 다른 창의 칸 누르기, 새 창(터미널) 뜨기: 조합하던 글자가 원래 칸에 한 번만 확정된다
    - 한글·영어(대문자)·숫자 섞어 치기, 터미널(foot)의 cat이 받은 UTF-8 바이트(조합 중 Enter 포함), Firefox 글 칸에서 조합 중 Tab과 다른 칸으로 옮기기
    - 그래픽 세션이 있는 arm64에서만 돈다. 자체 컴포넌트가 없는 이미지(지금의 x86-64)에서는 e2e 5·6번처럼 건너뛴다
    - 만들며 찾아 고친 것: 조합 중 다른 창을 누르면 글자가 사라졌다(컴포지터가 키보드 포커스를 옮기기 직전에 확정한다). 터미널에서 조합 중 Enter를 누르면 가끔 마지막 글자가 줄바꿈 뒤로 갔다(입력기의 commit serial이 어긋나면 smithay가 앱에 done(0)을 보내고 foot은 그 done을 버린다. 늘 글 입력의 serial로 보낸다). 왼쪽 Shift만 눌렀다 떼면 영문으로 바뀌었다(fcitx5 기본 단축키 AltTriggerKeys를 끈다). GTK4 앱의 창 안에서 다른 칸을 누르면 조합하던 글자가 사라지는 것은 GTK의 동작이라 남았다([개발 환경](../dev/environment.md) 7장)
  - e2e 7번(2026-10-30, `tests/e2e/session-lock.sh`)은 e2e 4번에 이어 돈다. QMP로 ⌃⌘Q를 넣어 잠그고, 잠금 화면이 뜨는지(`GetLocked`, 저널의 `bunt-lock: ready`), 잠긴 동안 에이전트의 스냅샷과 앱 목록이 거절되는지, 틀린 암호로는 풀리지 않는지, 잠금 화면에 QMP로 친 암호로 풀리는지, 풀린 뒤 에이전트가 다시 읽는지 본다. 잠금은 사람의 암호로만 풀리므로 시험도 그 길로만 푼다
  - 시나리오는 드라이버에 독립적인 형식(단계 = {동작, 기대값})으로 작성하고, Phase 3에는 드라이버만 교체한다
- 시나리오 예 (워크플로우 단위):
  1. 부팅 → 로그인 → 셸 표시
  2. 터미널 실행 → `apt install` → 스냅샷 생성 확인 → 롤백
  3. 컨테이너로 웹 서버 실행 → 로컬 포트 응답 확인 (호스팅 시나리오)
  4. 한국어 입력: 텍스트 필드에 한글 조합 입력 후 값 검증
  5. 에이전트가 앱 A의 값을 읽어 앱 B에 입력 (앱 간 제어)
  6. 에이전트가 `sensitive` 동작 시도 → 승인 UI 표시 → 에이전트 seat로 승인 불가 확인

### 9.4 CI 구성 (ADR-010)

- 저장소: GitHub 공개 저장소 [`blackmallangcow/buntOS`](https://github.com/blackmallangcow/buntOS). 실기기(TB375FC) 시험을 마친 뒤 공개하며(2026-10-30 결정), 그 전까지는 비공개로 두고 aarch64 빌드·e2e는 로컬 개발 VM(`tools/devvm/`)에서 돌린다(arm64 호스티드 러너 무료 제공은 공개 저장소 한정)
- x86-64 e2e: GitHub 호스티드 Linux 러너에서 KVM 가속으로 전체 시나리오를 돌린다
- aarch64 e2e: Phase 0 첫 주에 호스티드 arm64 러너(`ubuntu-24.04-arm`)의 `/dev/kvm` 유무를 확인해 둘 중 하나로 확정한다
  - KVM 있음: 호스티드 arm64 러너에서 전체 시나리오
  - KVM 없음: PR에서는 TCG로 핵심 시나리오를 돌린다. 가속이 필요한 전체 시나리오는 리뷰를 마친 코드에 한해 메인테이너의 Apple Silicon Mac에서 실행하고(비공개 미러 저장소의 self-hosted 러너 또는 로컬 실행), 그 결과를 병합 전 확인 항목으로 둔다(9.1)
- 공개 저장소에는 self-hosted 러너를 연결하지 않는다. 포크 PR 코드가 러너 머신에서 실행될 수 있기 때문이다
- 호스티드 러너의 디스크 제약(arm64 러너 기준 SSD 14GB)에 맞춰 이미지 빌드 캐시와 산출물 크기를 관리한다
- 라이선스 표기 검사(`reuse lint`)를 CI에 포함한다(D10)


- 이미지 빌드 도구: mkosi (Debian 지원, 아키텍처별 빌드, UKI 생성)
  - 루트는 내용에 맞춘 작은 btrfs로 만들고(`Minimize=guess`), 처음 켤 때 systemd-repart(`/usr/lib/repart.d/10-root.conf`)가 파티션을, systemd-growfs-root(GPT 속성 59)가 파일 시스템을 디스크 끝까지 늘린다. 16G 디스크에서 5.4G가 15.4G가 되었고 둘을 합쳐 0.1초 남짓 걸렸다. 전에는 루트에 여유가 거의 없어 VM에 앱 하나(Claude 데스크톱 앱)를 설치하자 디스크가 찼다
- 패키지 형식: 자체 컴포넌트도 .deb로 패키징하여 일반 Debian 패키지와 같은 경로로 배포/업데이트
- 패키지 미러: snapshot.debian.org의 특정 시점으로 고정하고, 주 1회 갱신 PR(e2e 통과 시 병합)로 올린다. forky 정식 릴리스 전의 공개 빌드에는 "보안 지원 없음"을 표시한다(ADR-004)
- Rust 툴체인: `rust-toolchain.toml`로 고정하고 Debian rustc에 의존하지 않는다(ADR-004)
- 라이선스 표기: 파일마다 SPDX 헤더를 달고, 헤더를 달 수 없는 파일은 `REUSE.toml`로 표기한다(D10)

- 검토 반영과 버스 고침을 더 합쳐 다시 확인했다(2026-10-30 오후): e2e 1·5·6·7번 통과(전원 꺼짐까지 229초). 세션의 터미널에서 `nmcli dev wifi connect`로 켠 연결은 Wi-Fi 암호 창이 키보드를 가져가지 않고(친 글은 터미널로 간다), 메뉴 막대에서 고른 네트워크는 가져간다. 창의 [취소]는 nmcli에 "Secrets were required, but not provided"로 돌아간다
  - 이때 Mac이 바빠(스왑 8GB) 시험 VM의 Firefox가 첫 페이지를 띄우는 데 1분 가까이 걸려 e2e 5번의 Firefox 확인 여섯이 실패했다. Firefox 주 프로세스가 CPU를 다 쓰는 동안 셸과 컴포지터는 쉬고 있었고, 시험이 페이지와 누른 결과를 기다리게 고친 뒤 통과했다. main의 이미지와 견주려던 빌드는 공유 cargo 대상 디렉터리가 앞 빌드의 바이너리를 그대로 써서 비교가 되지 않았다([개발 환경](../dev/environment.md) 4장)
- 한글 입력 e2e (2026-10-30, 다음 작업 5번): e2e 4번(`tests/e2e/hangul.sh`)이 QMP로 넣은 키가 실제 조합 길(libinput → 컴포지터 → fcitx5 → 앱)을 거치게 하고 25가지를 본다. ⌃스페이스·한/영 전환과 메뉴 막대 표시, 2벌식 조합(쌍자음, 겹모음, 받침 넘김, 조합 중 Backspace·문장 부호), 조합 중 입력 소스 전환·다른 창 누르기·새 창, 한글·영어·숫자 섞기, 터미널(foot)이 받은 UTF-8 바이트, Firefox 글 칸이다. 다른 AI가 만든 것을 이 세션이 main에 옮겨 마무리했다
  - 만들며 고친 것: 조합 중 다른 창을 누르거나 화면을 잠그면 컴포지터가 조합하던 글자를 확정한다. 입력기 commit의 serial이 어긋나도 앱에 그대로 적용해, 터미널에서 조합 중 Enter를 눌러도 글자 차례가 맞다. fcitx5의 왼쪽 Shift 전환을 껐다
  - e2e 드라이버: 6·4·7번이 같은 도우미를 쓴다. 게스트에 스크립트를 넣을 때 줄마다 답을 기다리고 sha256을 견주며, Firefox가 늦게 뜨면 기다린다. 전체 제한 시간은 1200초다
  - arm64 QEMU에서 e2e 1·5·6·4·7번을 한 부팅에서 통과했다(전원 꺼짐까지 369초). x86-64는 그래픽 세션이 아직 없어 돌리지 않았다(Phase 1 종료 조건의 나머지, 다음 작업 4번)

다음 작업 (제안 순서, 2026-10-30 갱신)

1. 알려진 문제(작은 것):
   - 에이전트의 포인터 누르기가 일반 창만 찾아서, 셸에 붙은 단추(메뉴 막대 시계, Dock)를 포인터로 누르면 "the compositor has no window for this app"으로 실패한다. 셸 표면도 찾게 하되 인증 창은 계속 거절한다
   - bunt-shell이 30분마다 `g_variant_get_variant` 경고를 여러 줄씩 낸다. 트레이 항목(StatusNotifierItem)의 메뉴를 채울 때 이미 꺼낸 값을 다시 꺼내서로 보인다. 메뉴는 대체 경로로 채워진다
   - polkit 인증 에이전트, Wi-Fi 비밀 에이전트, Bluetooth 페어링 에이전트, 앱 항목(StatusNotifierItem)은 아직 gio-rs의 이름 감시를 그대로 써서, 버스 데몬이 갑자기 끝나면 셸이 같은 자리에서 죽는다(gio-rs가 NULL 연결을 unwrap한다). Bluetooth와 입력 소스처럼 `dbus::watch_name`으로 옮긴다
   - 메뉴 막대의 Wi-Fi는 첫 Wi-Fi 장치를 쓰고, 이 기기의 핫스팟(AP) 연결도 알고 있는 네트워크로 센다. Wi-Fi 장치가 여럿이고 첫 장치가 핫스팟이면 그 장치로 연결하려다 핫스팟을 끊는다(2026-10-30 hwsim 시험). 시스템 설정은 핫스팟이 아닌 장치를 고르고 핫스팟 연결을 빼므로 셸도 그렇게 맞춘다
   - GTK4 앱의 한 창 안에서 한글을 조합하는 중에 다른 칸을 누르면 조합하던 글자가 사라진다. GTK4가 칸이 포커스를 잃을 때 조합 글자를 버리고 다음 칸에서 글 입력을 다시 켜서다. 다른 창을 누를 때와 화면을 잠글 때는 컴포지터가 확정한다. GTK 쪽 고침이 필요하다(개발 환경 7장)
   - 메뉴 막대는 Wi-Fi가 주 연결일 때만 연결된 네트워크를 맨 위에 보인다. 유선이 함께 연결돼 있으면 연결된 Wi-Fi가 알고 있는 네트워크 사이에 섞인다(macOS는 연결된 Wi-Fi를 늘 위에 보인다)
2. Agent Control Plane 3단계(REPL과 MCP, `wait`, 6.6절). 외부 AI 클라이언트가 MCP로 붙게 한다. 읽기·동작 경로(1·2단계)와 스크롤은 2026-10-29에 넣었다. Chromium·Electron 앱에서도 화면 밖 요소와 휠 스크롤을 확인한다(지금까지는 Firefox와 GTK4 앱으로 시험했다)
3. 단축키 화면의 남은 것: 최소화 효과(지니·축소)와 데스크탑 및 Dock 페이지의 최소화 설정, 화면 기록(⇧⌘5의 기록 단추), 끌어서 고친 뒤 찍는 선택 영역([디자인 스펙](DESIGN-SPEC.md) 15장). 창의 최소화 단추와 Dock의 최소화 칸, ⌘⇥ 앱 전환 창, 스크린샷 미리 보기와 ⇧⌘5 도구 막대는 2026-10-30에 넣었다
4. x86-64 그래픽 세션: x86-64 이미지에도 자체 컴포넌트를 넣고, CI 호스티드 러너에서 빌드와 e2e 1·5·6·4·7번을 돌린다(Phase 0 종료 조건, 한글 입력 e2e를 양 아키텍처에서 통과하는 Phase 1 종료 조건). 필수 드라이버를 넣은 x86-64 이미지의 빌드와 e2e 1번은 로컬에서 통과했다(2026-10-28)
5. GPU 경로 확인과 bunt-comp 기본기의 남은 것: virgl(`VMCTL_GPU=virgl`)과 하드웨어 GPU에서 linux-dmabuf와 GTK의 GL·Vulkan 렌더러를 확인한다. 앱 버퍼의 직접 스캔아웃과 표면마다의 피드백, 시스템 설정 사이드바의 흐림 요청을 더한다. smithay 0.7에서 찾은 문제 둘(dmabuf 평면 검사의 u32 넘침, 끊긴 앱의 기본 피드백이 남는 것)을 올려 보낸다. 화면 장치와 GPU가 다른 SoC(대상 기기)에서 KMS가 있는 장치를 고르는 것은 실기기 2c·2e 단계에서 한다
6. 세션의 남은 것: 쓰지 않으면 잠그기와 잠금 화면 설정, 빠른 사용자 전환(5.4절), 컴포지터의 ptrace 막기(이미지의 Yama `ptrace_scope`), 메뉴의 단축키 기호, 세션 스크립트가 부르는 프로그램(`systemd-cat`, `bunt-comp`)의 절대 경로
7. 시스템 서비스 에이전트의 남은 것: 실제 Bluetooth 기기(또는 Bumble 가상 컨트롤러)로 페어링 창 확인, 새 802.1X(회사·학교) 연결 시트, 알림 배너 쌓기, 앱별 알림 설정의 하위 화면, 잠금 화면의 알림 미리 보기
8. 메모리·프레임 기준선 기록 (Phase 1 종료 조건). ADR-001의 Qt6 시제품을 만들어 GTK4 시제품(bunt-shell v0, bunt-settings v0)과 비교 측정한다
9. 실기기 실측 보고서: TB375FC를 받은 뒤 12장 항목을 잰다 (Phase 0 종료 조건)
10. 저장소 공개 전환: 실기기 시험을 마친 뒤에 한다(2026-10-30 결정, [결정 자료](DECISION-BRIEF.md) 0.3절). 공개 이미지에서는 직렬 콘솔의 root 자동 로그인을 막고, e2e는 시험 계정의 sudo로 바꾼다

| 커널 버전/설정 | `uname -a`, `cat /proc/version`, `zcat /proc/config.gz` (읽기 권한은 기기마다 다름) | 벤더 드라이버 목록(포팅할 하드웨어 블록 식별), GenieZone/KVM 관련 옵션 |

| 부트 구성 | `getprop ro.boot.slot_suffix`, `getprop ro.boot.dynamic_partitions`, `ls -l /dev/block/by-name/` (권한 허용 범위) | A/B, super 파티션, vendor_boot 유무 |

### 12.1 EL2/KVM 판정

리눅스가 KVM을 쓰려면 커널이 EL2에서 시작해야 한다. MediaTek에는 EL2에서 동작하는 자체 하이퍼바이저 GenieZone이 있고, 이것이 EL2를 차지하면 OS 구성과 무관하게 KVM을 쓸 수 없다(4.2.1-6).

| 시점 | 확인 | 해석 |
|---|---|---|
| 언락 전 (adb) | `ls -l /dev/kvm /dev/gzvm` | "No such file"이면 노드가 없다. "Permission denied"면 노드는 있다 |
| 언락 전 (adb) | `getprop \| grep -i hypervisor` | 안드로이드 가상화 프레임워크(AVF)용 하이퍼바이저 지원 표시 |
| 언락 전 (adb/호스트) | `zcat /proc/config.gz \| grep -i -E "KVM\|GZ"`, 벤더 DTB에서 `grep -i geniezone` | 벤더 커널의 KVM·GenieZone 사용 흔적 |
| 언락 후 (2a 단계) | mainline 커널 부팅 로그의 `CPU: All CPU(s) started at EL2`(또는 `EL1`)와 kvm 초기화 메시지 | 최종 판정 근거 |

판정

- **가능**: 커널이 EL2에서 시작하고 mainline 커널에서 `/dev/kvm`이 생성된다 → 동등성 매트릭스의 가상화 항목(4.4-5)을 실기기에도 적용한다
- **불가 (EL2 점유)**: 커널이 EL1에서 시작하고 GenieZone 흔적이 있다 → OS로는 해결할 수 없다. 원인과 함께 D9 예외로 기록하고 ADR-011(기기 선택)의 입력으로 올린다
- **미정**: 안드로이드 측 신호는 예비 판정일 뿐이다. 신호가 엇갈리거나 부족하면 2a 단계의 부팅 로그로 판정한다
